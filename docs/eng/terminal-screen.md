# 屏幕归谁管

<Badge type="info" text="agent-platform · CLI 渲染 · 2026-08-25" />

终端、shell、程序三层各自负责什么；备用屏是什么、它白给了什么又拿走了什么；我们最后选的那一套（ADR-0058）为什么是那样；以及如果重来一次，这个需求该怎么写才不会走三轮弯路。

- **3** 层：终端 / shell / 程序
- **2** 块屏幕缓冲区
- **688** 行代码因备用屏而写
- **142** 行测试因它而删

## 三层是怎么连起来的

连接只有一样东西：**一条双向的字节流**。没有 API 调用，没有函数接口，全是字节。理解这一点，那几个界面 bug 会同时变得可解释。

<figure class="diagram">
<!--@include: ./figures/terminal-screen-1.svg-->
<figcaption>程序跑起来之后，字节是终端和它直接来回的。shell 只是介绍人：创建好连接、把 fd 交出去，然后退到一边等。所以程序崩了 shell 还在，`Ctrl+C` 的含义也由程序自己定。</figcaption>
</figure>

唯一例外是管道。`claude -p "..." | grep x` 时 shell 把 stdout 接到管道而不是 pty，程序一探测 `isatty()` 为假就关掉颜色和整个界面。CI 里跑无头模式走的就是这条路。

## 终端到底是什么

它就是一块屏幕加一个键盘，用软件做的。全部职责只有两件：把别的程序丢来的字符画到屏幕上，把你的按键送给那个程序。**它不认识任何命令。**

### 一个能立刻验证的实验

```text
$ gti status
bash: gti: command not found
```

这句话不是终端说的。终端只是把这几十个字符画在了屏幕上，它根本不知道 `gti` 是什么。这句话是 shell 说的——shell 去 PATH 里找了一圈没找到，生成了这句话，交给终端去画。

### 判断归属最实用的办法：看设置

| 你在调的东西 | 归谁 | 为什么 |
| --- | --- | --- |
| 字体、配色、透明度、光标形状 | 终端 | 画面是它画的 |
| 标签页、分屏、复制粘贴用什么键 | 终端 | 窗口是它的 |
| 往上能翻多少行 | 终端 | 滚动历史是它持有的 |
| 提示符长什么样、PATH、别名 | shell | 命令是它解析的 |
| `ls` 还是 `dir`、通配符怎么展开 | shell | 同上，所以换 shell 就换一套语法 |

名字的来历：早年终端是真的硬件，一台只有屏幕和键盘的设备，用电缆连到另一个房间的主机，自己不做任何计算。后来硬件消失了，但程序仍按「我在对一台终端说话」的方式写，于是有了模拟它的程序——terminal emulator，终端模拟器。

## 两块缓冲区

终端里有两块屏幕缓冲区。这是终端几十年前就有的能力，终端提供，我们只是写一串 `ESC[?1049h` 请求它切过去。

<figure class="diagram">
<!--@include: ./figures/terminal-screen-2.svg-->
<figcaption>两块缓冲区的差别只有三条：有没有滚动历史、程序管几行、退出后剩什么。选了任何一条，另外两条就跟着定死了。</figcaption>
</figure>

### 你肯定用过

```text{1,2}
$ less README.md   ← 整屏被占满，按 q 退出后一点痕迹都没有
$ cat README.md    ← 内容留在滚动历史里，滚轮往上翻还能看到
```

`vim`、`top`、`man` 全是前者。程序要进备用屏，是因为它想独占整个屏幕：留在主屏时它不能随便清屏（会擦掉别人的东西），也不能说「我要把这个框钉在第 41 行」——那一行不归它管。

## 我们选的那一套

决定在 ADR-0058。直接目的是产品需求：用户要「刚进 CLI 输入框就在屏幕底部」。五条落地：

| # | 做法 | 关键细节 |
| --- | --- | --- |
| ① | 交互路径进备用屏 | 交给 ink 的 `alternateScreen: true`，不自己写序列；退出还原要覆盖正常 unmount、Ctrl+C、未捕获异常三条路径 |
| ② | 帧高等于 `rows`，输入框恒在最后一行 | 内容区与页脚之间一格 `flexGrow` 撑开，不靠空格占位 |
| ③ | resize 一律先整屏清再全量重画 | 不再判断终端会不会 reflow——判断需要的那个事实不可观测 |
| ④ | 历史由程序自己持有，`<Static>` 退场 | 上翻与滚轮因此既成为可能，也成为必须 |
| ⑤ | 保留「永不写满最后一列」 | 在备用屏里仍然必要，因为我们留在 ink 上 |

第 ③ 条是关键的认知转换。整屏清这一招在主屏时期被否决过（ADR-0057 ③），理由是 scrollback 会出现重复行、启动前的 shell 输出会被擦掉——**而那两条说的都是主屏**。备用屏里压根没有那些内容，这一笔于是变得没有代价。

::: tip
**备用屏不是解法，是让那个解法变得没有代价的前提**。如果只搬进备用屏、别的什么都不做，残影照样会叠——擦除算术错在 ink 那里，跟你在哪块缓冲区上画没有关系。真正保证「放大缩小不重复」的，是我们自己写的那一笔 `ESC[2J`（`resize-clear.ts`），而且它必须用 `prependListener` 抢在 ink 的监听器前面，否则会把刚画好的那一帧擦掉。
:::

还有一条铁证说明备用屏没有天然消掉这类问题：ADR-0058 ⑤ 保留了「永不写满最后一列」。

> 它在备用屏里仍然必要，因为我们留在 ink 上：ink 写出的是一整块以 `\n` 分行的文本，某一行写满最后一列就会自动换行，把整帧往下顶一行。参考实现不受这条约束是因为它逐行绝对定位——那是方案 B 的性质，不是备用屏的性质。
>
> —— `ADR-0058 ⑤`

## 之前为什么修了那么多轮

根因不是一个，是三件事叠起来的（ADR-0057 背景）：

- 输入框每一行恰好等于终端宽度——带边框的 Box 在纵向容器里默认横向撑满
- ink 擦上一帧按**逻辑行数**（`str.split("\n").length`），而 `eraseLines(n)` 数的是终端行
- 写满最后一列的行在 conhost / Windows Terminal 上占两个终端行

于是每次重绘擦 4 行、实占 6 行，每敲一个字净剩两行残影。改尺寸不是根因，是放大器：一次拖拽触发几十次重绘，而且变窄时终端会把旧行按新列宽回流——156 列的 3 行帧到 120 列变成 7 行，ink 仍只擦 4 行，每缩一次净剩 3 行。

::: tip
**前两轮修不好的共同原因不是技术，是没拿现象核对假设**。用户截图是零对话、甚至没 resize 就已经叠了五个框，而当时的两个假设都需要「有历史」或「发生过 resize」才成立。
:::

## 备用屏给了什么，拿走了什么

::: info 白给的 — 终端
- 退出后终端还原成进来之前的样子——终端自己做的，我们一行代码都没写

只有这一项。
:::

::: info 拿走的 — 我们
- 原生滚动历史没了 → 上翻、滚轮、视口位移要自己实现
- 鼠标拖选被接管 → 覆盖层（ADR-0073）
- PageUp 被终端吃掉 → 与 `Ctrl+U`/`Ctrl+D` 双绑

这三条是备用屏新欠下的债。
:::

::: info 本来就得自己做的 — 我们ink
- resize 整屏清那一笔、不写满最后一列、每帧画什么
- 进出备用屏、隐藏与还原光标、擦上一帧——这些归 ink

跟在哪块缓冲区上画无关。
:::

最后一行是踩出来的。`resize-clear.ts` 的头注释记着：

> 第一版是自己写 `ESC[?1049h/l`，绕过了 ink 那套，直接后果是真实光标没被隐藏，用户看到一个游标停在输入框尾部、跑动时停在框下面。能交给框架的就别自己写第二遍。
>
> —— `apps/cli/src/view/resize-clear.ts`

也就是说：进了备用屏不等于光标正确，是「用 ink 的方式进备用屏」才正确。

## 这笔交换划不划算

### 开发成本：约 688 行

| 文件 | 行 | 干什么 |
| --- | --- | --- |
| `mouse-surface.ts` | 190 | 鼠标覆盖层 |
| `use-content-viewport.ts` | 171 | 上翻、滚轮、视口位移 |
| `terminal-selection.ts` | 163 | 拖选与复制 |
| `mouse-reporting.ts` | 67 | 开关鼠标上报 |
| `resize-clear.ts` | 56 | 改尺寸整屏清 |
| `diff-viewport.ts` | 41 | diff 的视口 |
| 合计 | 688 | 同时删掉 `resize-sweeper.ts` 与它 142 行测试 |

`fake-terminal.ts` 那 482 行不计入——它是主屏时期就已经建的终端模型（ADR-0057 ⑤），备用屏只往里加了「两块缓冲区」这一条语义。

### 关键：不是免费变收费，是换了一组成本

::: info 留在主屏
- 成本形态：**猜不可观测的终端时序**
- 上界：没有——参考实现为此连修八版，修完仍有残余风险
- 依赖：ink 的内部实现细节（没有公开承诺，会随版本变）
- 出错时：测试绿、真机红
:::

::: info 搬进备用屏
- 成本形态：**写确定的代码**
- 上界：688 行，写完就结束
- 依赖：`ESC[?1049h` 这个几十年没变的公开约定
- 出错时：屏幕断言直接报红
:::

被消掉的不是工作量，是不确定性。ADR-0058 的后果第一条写的是「resize 残影这一整类问题消失」，不是「变少」。

### 运行时代价：真实存在，已付过一次账

- 每帧从「几行」变成「整屏」——`Box height={rows}`，41 行 × 156 列全量重画
- yoga 每帧要给整棵树算布局，转圈时每秒十几次
- 历史由程序自己持有，长会话的内存与每帧折行成本自己管

第二笔已经优化过：跟随态只挂最近 `rows` 轮——屏幕上只显示最后一屏，更早的那些无论如何都在裁剪框外，挂上去只是让 yoga 白算一遍。浏览态则故意不优化，全量挂载，理由是「用一点开销换一行都不用猜」。

::: tip
**引信已经埋好**。ADR-0058 的重估触发条件第一条：全屏下 spinner 每 80ms 整帧重绘出现肉眼可见的闪烁、且降频或「仅状态行变化时重绘」无效，就走方案 B（照参考实现逐行绝对定位、ink 退场）。那是 ink「整块写出」与全屏刷新的固有张力，不是参数问题。
:::

## ink 在哪一格

ink 是第三方 npm 包（`ink@7.1.1`，包描述就四个词：React for CLI），既不是系统自带，也不是我们写的。它把 React 组件渲染成一整块文本写进 stdout，布局引擎是 yoga。

**用不用 ink 和进不进备用屏是两个互相独立的决定**。四种组合都有真实例子：

|   | 主屏 | 备用屏 |
| --- | --- | --- |
| 用 ink | ADR-0057 时期的实现；Claude Code 也是这个形态 | **我们现在** |
| 不用 ink | 手写 ANSI 局部重绘（ADR-0056 否决方案 B） | 参考实现 `local-ai-assistant`：逐行绝对定位自己写渲染器 |

选 ink 的两条决定性理由（ADR-0056）：中文全角显示宽度，以及不自己写渲染器。否决手写 ANSI 那段说得最直白——手写就得自己接一个宽度库，「零依赖」的优势当场消失一半；剩下的折叠、输入框、焦点、重排要自己实现，按体量线几乎必然拆成一个自研微框架，等于「用一个自研微框架换掉一个成熟框架」。

### 实际有三条渲染路径

| 路径 | ink | 备用屏 | 什么时候走 |
| --- | --- | --- | --- |
| 交互式 | 用 | 进 | 两端都是 TTY |
| 行式输出 | 不用 | 不进 | 管道、CI、带一句话直接跑一轮 |
| 测试 | 用（假终端） | 可开可关 | `ink-tty-harness` 的 `altScreen` 参数 |

第二条不是遗留物。`index.ts` 头注释：「那条路径不是遗留物，是无人值守场景的正路。」

## 如果重来一次，需求该怎么写

失败点不是技术选错，是需求写在了错误的抽象层上。ADR-0056 当初把需求写成「CLI 形态定在第 3 层」——那是实现层的分类。靶子没立错，靶子上少了用户在意的那一环：「刚进来输入框在屏幕哪个位置」不在那道题里。

### 只写用户看得见的六件事

- 启动那一刻，输入框在屏幕最底行，还是紧跟在正文下方
- 退出之后，整段对话留在滚动区能往上翻，还是终端还原成进来之前的样子
- 内容超过一屏时，用终端自己的滚轮，还是程序自己的上翻键
- 鼠标能不能拖选复制
- 改窗口大小之后，屏幕上应该是什么样
- PageUp、滚轮、Ctrl+C 归终端还是归程序

三轮返工的全部内容就是第一条，而它当初没有被问。

### 更省的写法：这六条只有两个自洽的套餐

::: info 套餐 A · 主屏
- 参照物：`git log`、Claude Code
- 输入框跟在正文下方，正文少时不贴底
- 退出后对话留在滚动区
- 终端原生滚动与拖选都可用
:::

::: info 套餐 B · 备用屏
- 参照物：`vim`、`less`、`top`
- 输入框恒在最底行
- 退出后终端一片干净，什么都不留
- 上翻与拖选都要程序自己做
:::

选了任何一条，就等于选了整套。想要「输入框贴底」又想要「退出后对话还在」，这两个不共存——这正是当初该在需求阶段说清楚、而不是到第三轮才发现的事。所以最省的表达方式是指一个真实程序：**我要 less / vim 那种全屏应用，不要 git log 那种滚屏输出。**

### 一份可以直接抄的需求模板

```text{3,5}
形态：全屏（备用屏），参照 less / vim。
启动那一刻：输入框在屏幕最底行；正文从顶部排，不足一屏时空白留在中间。
退出之后：终端还原成启动前的样子，对话不留在滚动区。  ← 接受这条代价
翻历史：程序自己实现，PageUp/PageDown 与 Ctrl+U/Ctrl+D 双绑，滚轮可用。
鼠标：拖选由程序接管；Shift+拖 走终端原生。            ← 接受这条代价
改尺寸：任何宽度下，屏幕上只有一个输入框，且在最后一行。
按键：Ctrl+C 一次中断当前轮，两次退出。
不做：退出后把转录打回主屏。
```

倒数第三行就是那个 bug 的验收标准。今天 `app-geometry.test.tsx` 断的正是这句话的机器版本，包括那条故意关掉清扫、断言残影必然出现的反向用例。**需求写得对的时候，验收断言几乎是照抄的。**

::: tip
**还要带上两样元信息**。其一，对标对象要带核验日期和具体哪条渲染路径——ADR-0058 就是靠「参考实现已经不在 v9 了」这个新事实翻的案，而它的旧文件头写着一整套自洽的旧模型，读起来毫无破绽。其二，明确写出接受哪些代价：ADR-0057 ⑦ 那条「正文少时输入框在正文下方」被识别、被记录，然后被自己批准了。一条代价只要用户能一眼看见，它就不是实现细节，是需求。
:::
