# 沙箱与权限的三种解法

<Badge type="info" text="Codex · Claude Code · DeepSeek Harness" />

让一个模型在你的电脑上跑命令，只有两种办法拦住它干坏事：**在它动手之前判断这条命令危不危险**，或者**让它动手，但把它关在一间它拆不开的屋子里**。三家开源智能体给出了这道题的三个不同答案——一家两样都做，一家只做前者，一家干脆只做后者。这份文档把它们逐层拆开，先讲人话，再上细节。

<Badge type="tip" text="放行" /> 直接执行，不打扰人 <Badge type="warning" text="问人" /> 弹框等一次答复 <Badge type="danger" text="拦住" /> 不执行，且不给商量

**核验日期** 2026-08-23 至 08-25 · **证据来源** codex / dsh 读源码，Claude Code 读行为规格与 Python SDK · **没有一条是实测** 三家都没跑起来验证

## 「权限校验」和「沙箱」不是一回事

<Badge type="info" text="01 · 先把两个词说清楚" />

::: info 打个比方
**权限校验**是门口的保安：他看一眼你要干什么，对照一张名单，决定放你进去、拦下你、还是打电话问屋主。他判断的依据是你*说*你要干什么。

**沙箱**是屋子本身的锁：哪怕保安放你进来了，你也只能打开被允许的那几扇门，其余的推不动。这些锁不是这个程序自己装的，是操作系统装的——**程序自己拆不掉**。
:::

这个区别之所以要紧，是因为两者的失效方式完全不同。保安可以被话术绕过：同一件事换个说法、换个包装、多打几个空格，名单就对不上了。而锁不会被话术绕过，它只认系统调用——代价是每个操作系统的锁长得不一样，而且有些门它*确实锁不住*。

一次工具调用要经过的完整链条，三家的形状高度一致，可以先记住这四段：

| 阶段 | 在干什么 | 说人话 |
| --- | --- | --- |
| 风险判定 | 这次调用属于哪一档 | 保安扫一眼 |
| 审批 | 需要人点头吗，谁来点这个头 | 拿不准就打电话 |
| 受约束执行 | 在什么边界里真的跑起来 | 屋里的锁在这一步起作用 |
| 留证 | 谁批的、批了什么、结果是什么，写进日志 | 门禁记录 |

三家的差别不在于有没有这四段，而在于**把重量压在哪一段**——以及一个更根本的问题：第一段到底该判命令的字面，还是干脆不判。

## 一道题，两种答法

<Badge type="info" text="02 · 那道分岔" />

模型发来一条 `rm -rf build/`，该怎么办？两条路在这里分开，而且它们不是「实现细节不同」，是**两种世界观**。

<figure class="diagram">
<!--@include: ./figures/sandbox-1.svg-->
<figcaption>同一条命令的两条路。上半：判定器是唯一一道网，它漏掉的那条命令直接就落地了。下半：没有判定器，撞墙是常态，而<b>审批框由一次真实的拒绝触发</b>，不由命令内容触发。</figcaption>
</figure>

### A 的代价：判定器一定有漏判形状

Claude Code 自己的文档在讲完一整套命令匹配规则之后，加了一条警告：**试图靠模式约束命令参数是脆弱的**。它用 `curl` 举了五种绕法——flag 写在前面、换个协议、跟随重定向、把地址塞进变量、参数之间多打几个空格。它给的替代方案不是「再补几条规则」，而是「干脆 deny 掉 curl / wget，改走按域名放行的抓取工具，或者用一个钩子自己校验」。

一份把命令字面抠到词边界级别的规范，在结尾说这条路是脆的——这是这道分岔上最直接的一次表态。

### B 的代价：需要每个平台都有一把锁，还得给模型留一条体面的台阶

沙箱不是免费的：Linux、macOS、Windows 三套机制完全不同，写起来是三份实现（codex 光 Windows 那份就是一个 19,730 行的独立模块）。而且如果被拒之后没有退路，模型会原地卡死或者开始瞎试。所以 B 这条路必须配一条**升级通道**：撞墙 → 说明为什么需要更宽的权限 → 人点头 → 换一档重跑。

它换来的好处很实在：**判错的代价从「挡住了本该放行的事」降成「多跑一次」**。

::: info 三家站位
**Codex**：两样都做。硬编码的判定器被刻意做到极小，主策略挪进用户可编辑的规则文件，兜底压在沙箱上。<br> **Claude Code**：证据里只核到 A。它的隔离靠权限判定加执行护栏，没有核到进程级沙箱（这是[一个证据缺口](#gaps)，不是已证明的缺席）。<br> **DeepSeek Harness**：只做 B。没有命令白名单、没有词法器、没有风险分档，一条都没有。
:::

## 三家各是什么形状

<Badge type="info" text="03 · 速览" />

::: codex Rust · 约 100 个 crate
两个正交旋钮：**沙箱档**（只读 / 工作区可写 / 完全放开）× **审批策略**（四档）。用户可以只调其中一个。

执行是四步：审批 → 选沙箱 → 试跑 → **被拒就换更宽的沙箱重试，而且不重新问人**。

裁决者有三级：钩子、一个**模型审查员**、人。
:::

::: claude 行为规格 · Python SDK 源码
主力是一套**六步固定定序**的权限判定，顺序写死：钩子 → 拒绝规则 → 询问规则 → 权限模式 → 允许规则 → 回调。

外加一套抠到词边界的 bash 匹配规则：复合命令逐段判、包装命令按固定表剥离、未加引号的通配符要额外小心。

钩子有 31 个生命周期事件，是最丰富的一家。
:::

::: dsh TypeScript · 234 个包
沙箱接缝只有一个方法 `confine(argv, policy)`。**「悄悄地不加约束直接放行」在类型上就是非法的。**

最独特的一条：**「这次到底管住了多少」是一个被报出来的事实**——`full` 还是 `partial`，后端必须说实话。

审批结果是封闭四值，只有一个值放行，其余全部倒向拒绝。
:::

## 两个旋钮、极小的判定器、外置的规则

<Badge type="info" text="04 · Codex" />

::: info 一句话
codex 的思路是：**别指望靠读命令猜出危险，把力气花在「屋子锁得住」和「规则可以被人编辑和审计」上**。判定器只留了一条真规则，其余全交给外置策略文件和沙箱。
:::

### 两个旋钮：沙箱档 × 审批策略

这两件事在 codex 里是**正交的**——你可以要一个很紧的沙箱配上很松的审批，反过来也行。很多设计把它们绑成一个「安全等级」滑块，codex 没有。

| 旋钮 | 取值 | 说人话 |
| --- | --- | --- |
| `sandbox_mode` | `read-only` | 什么都不许写 |
|   | `workspace-write` | 只有当前项目目录可写（在版本控制目录下是默认档） |
|   | `danger-full-access` | 不上锁 |
| `approval_policy` | `on-request` | 默认档，需要时才问 |
|   | `never` | 永不问（无人值守场景） |
|   | `untrusted` | 只读的自动过，改状态的都要批 |
|   | `granular` | 按类别分别配 |

#### 锁本身用的是操作系统自带的机制

macOS 用 Seatbelt 的沙箱描述文件，Linux 用 bubblewrap 加 seccomp 与 Landlock，Windows 是一份独立实现（带受限令牌与私有桌面选项，19,730 行），WSL2 沿用 Linux 那套。这一点很关键：**这些都不需要容器、不需要虚拟机、不需要任何额外基建**，装上就能用。

网络默认是关的。打开之后走域名级策略：可以写精确主机名、写 `*.example.com` 这样的作用域通配、也可以写全局 `*`；**拒绝永远压过允许**；想让程序监听本机端口还得单独打开一个开关。三家里只有 codex 把网络管到了进程沙箱这一层。

### 执行的四步，和那个「不重新问人」的回环

编排器的四步直接写在源文件的头注释里，一个字都没多：

```text
approval → select sandbox → attempt → retry with an escalated
sandbox strategy on denial (no re-approval thanks to caching)
```

<figure class="diagram">
<!--@include: ./figures/sandbox-2.svg-->
<figcaption>被沙箱拒绝在 codex 里不算失败，算「这一档不够宽」。同一个工具的两次尝试携带两份不同的沙箱参数，第二次更宽；最宽那一档给不给，由一个单独的开关决定。</figcaption>
</figure>

### 裁决链：三级，而且「问谁」是可以换的

这是 codex 最值得抄的一条结构。判出「这事要批」之后，**由谁来批是一个独立维度**，换裁决者不用动判定逻辑。优先级在源码里写死：

| 裁决者 | 什么时候轮到它 | 说人话 |
| --- | --- | --- |
| 钩子 | 永远先跑，返回允许或拒绝就地结案 | 你自己写的一段脚本，插在最前面 |
| Guardian | 审批策略是 `on-request` 或 `granular`，**且**裁决者配成了自动审查 | 另一个模型当审查员 |
| 人 | 其余全部（默认就是这一档） | 弹框问你 |

#### Guardian 不是一段规则，是一个独立的审查会话

它的四步写在模块头注释里：重建一份压缩过的对话记录（保住用户的原始意图和最相关的近期上下文）→ 交给一个专门的审查会话去评估*这一次的具体动作*，要求它返回严格的 JSON → **超时（90 秒）、执行失败、输出不合法，一律按拒绝处理** → 按它的结论执行。

它的风险策略也是外置的，一份 Markdown 文件，按风险类目组织（数据外泄、破坏性操作……），每一类给判据加一条结论规则。三条原文的味道值得抄：

- 「载荷只要是从敏感数据派生出来的，它就同样敏感」
- 「授权你创建某个内容，不等于授权你把它发出去」
- 「敏感度不明时，先按最高档处理」

### 规则外置：一个能被 review、能进版本库、还自带测试的策略文件

真正的命令策略不在代码里，在 `.rules` 文件里，语言是 Starlark（Python 语法，但不允许有副作用）。按配置层分布：用户层、团队层、项目层（**只在这个仓库被信任时才加载**）。核心构造长这样：

```text
prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "prompt",
    justification = "Viewing PRs requires approval",
    match = ["gh pr view 7888"],
    not_match = ["gh pr --repo openai/codex view 7888"],
)
```

- `decision` 三选一：<Badge type="tip" text="allow" /> <Badge type="warning" text="prompt" /> <Badge type="danger" text="forbidden" />，**多条规则同时命中时取最严的那条**。
- `justification` 会直接出现在弹给你的审批框里——规则自己解释自己为什么存在。
- `match` / `not_match` 是**规则自带的用例**，加载时就验证。写错的规则在启动阶段就会被抓住，而不是等到某天误放行了才发现。
- 还有一个命令行入口可以单独测一条规则，直接打印命中了哪条、判成了什么。

命令按参数列表处理（也就是程序真正收到的那个数组，而不是一整行字符串）。遇到 `bash -lc "..."` 这种把脚本塞在参数里的包装：能安全拆开时（只有 `&&` `||` `;` `|` 串起来的线性链、没有变量展开）就拆开逐段判、取最严；一旦出现重定向、命令替换、变量或通配符，**整条按「一段不可分析的脚本」保守处理**。

#### 一张「永远不许进白名单」的表

::: info 打个比方
你可以告诉保安「以后凡是送快递的都放行」。但如果你说的是「以后凡是*拿着钥匙*的都放行」，那你其实是把整栋楼交出去了——因为拿钥匙的人可以开任何一扇门。
:::

codex 有一张 88 条的前缀黑名单，里面是 `bash` `sh` `zsh` `node` `python` `perl` `deno` `bun` `osascript` `cmd` `powershell` `npm run` `pnpm run` `env` `git` 这一类。它们**不许被用户批准成为一条永久的放行前缀**，理由就是上面那个比方：这些前缀等价于「任意代码执行」，批一次等于全批。

### 一处把「护栏不是沙箱」写成代码的分支

改文件的操作看起来只碰了项目目录之内的路径时，codex 仍然要多问一句「这台机器上到底有没有真沙箱」：

```text
// Only auto-approve when we can actually enforce a sandbox. Otherwise
// fall back to asking the user because the patch may touch arbitrary
// paths outside the project.
match get_platform_sandbox(...) { Some(_) => AutoApprove, None => AskUser }
```

理由写得很直白：路径可能是一个**指向项目外的硬链接**，静态判定看不出来。很多项目把「护栏不是沙箱」写成一句文档口号，codex 把它兑现成了一个运行时分支——**没有锁的时候，就别假装自己判得准。**

#### 反过来也成立：外面已经关好了就别再关一层

权限档有三态：托管、关闭、外部。后两个表示「有意不套 codex 自己的文件系统沙箱」——比如整个进程本来就跑在容器里。这时候改文件的操作直接自动批准。**部署形态被编码进了权限判定**，跑在容器里的人不必再交一次沙箱的税。

### 审批的取值域比「批 / 驳」宽得多

| 请求类型 | 你可以回什么 |
| --- | --- |
| 执行命令 | `accept` · `acceptForSession` · `decline` ·`cancel` · **`acceptWithExecpolicyAmendment`**（批准并顺手改一条规则） |
| 改文件 | 同上四项，外加 `grantRoot`（顺手把某个目录加进可写范围） |
| 权限变更 | 回一个权限子集，可以带上「本会话有效」的作用域 |

开了智能审批时，codex 还会**在升级请求里主动提议一条规则**给你看：「要不要以后这类命令都按这条规则处理？」管理员则可以从上层配置强制下发限制性规则，用户改不动。

::: info 一条容易想错的
codex 有一个 Code Mode：模型不发结构化的工具调用，而是**直接写一段 JavaScript**，在进程内的 V8 里跑。很容易以为「那这段脚本里的操作是不是绕过了审批」——不是。脚本里**每一次**工具调用都会挂起并回到宿主，走与普通工具调用**同一个入口、同一套审批与沙箱**。沙箱在这里是正交的兜底层，不是它的答案。
:::

## 定序即架构：六步走完，谁也插不了队

<Badge type="info" text="05 · Claude Code" />

::: info 一句话
Claude Code 把力气全部押在「判得准」和「顺序不能乱」上。它的核心不是一组规则，而是**一个固定顺序的六步流水线**——每一次工具调用都必须从第一步走到最后一步，任何一档「更宽松的模式」都推不翻前面更具体的拒绝。
:::

### 六步定序

<figure class="diagram">
<!--@include: ./figures/sandbox-3.svg-->
<figcaption>六步是固定顺序，不是一组可以互相压制的规则。注意第 ② ③ 两步：即使把权限模式开到最松的一档，它们照样生效。</figcaption>
</figure>

还有一条藏在第 ② 步之前：如果你直接拒绝了一个**裸工具名**（比如整个 `Bash`），这个工具在进入六步之前就已经被从模型的上下文里摘掉了——模型压根看不见它。

### 三条讲究

#### 一、有一类动作，任何模式都自动批不了

文档管这叫「没有任何模式能自动批准的动作」，是一条**穿透所有档位的最小审批集**：关键路径上的 `rm` / `rmdir`、向用户提问这个动作本身、标了「需要用户交互」的外部工具、以及组织策略设成必须询问的连接器工具。无论你把权限开到多松，这几样都会停下来等人。

#### 二、被自动批准的工具，永远到不了你的回调

文档专门用一个警告框强调这件事，SDK 甚至会在检测到「你传了一个审批回调，但你的配置让它永远不会被调用」时发一条进程警告。这是一个很容易踩的坑：**你以为自己的回调在把关，实际上它被上游的允许规则短路了。**

它给的解法很干净——想要每次调用都过一遍，别用回调，用钩子，**因为钩子在第 ① 步**。这句话背后是一个明确的分工：允许 / 拒绝规则是*策略*，钩子是*穿透一切的拦截点*，两者不该混为一谈。

#### 三、「不再询问」的存续期是不对称的

bash 命令和网页抓取的域名会**永久**写进仓库根目录的本地配置文件；而文件修改类的「不再询问」**只活到本次会话结束**，不落盘。机制上这是同一个东西的两个取值：一次批准可以顺手改策略，而改动有六种操作（增 / 换 / 删规则、改模式、增删目录）× 四个写入目标（用户级 / 项目级 / 本地 / 仅本会话）。

### 那套很细的 bash 匹配规则

规则语法是 `工具名(限定符)`，比如 `Bash(ls *)`。下面这些边界情形不是吹毛求疵，每一条都对应一种真实的绕法：

| 规则 | 它挡的是什么 |
| --- | --- |
| 词边界 | `Bash(ls *)` 匹配 `ls -la`，但不匹配 `lsof`；写成 `Bash(ls*)`（没有空格）两个都匹配。一个空格改变含义。 |
| 复合命令逐段判 | 用 `&& \|\| ; \| &` 和换行串起来的命令，**每一段都要独立命中**；批准一条复合命令时按子命令分别存规则，最多存 5 条。 |
| 包装命令剥离（内置且不可配） | 剥掉 `timeout` `time` `nice` `nohup` `stdbuf` `command` `builtin` `noglob` 和**不带参数的裸 `xargs`**，然后判里面那条真命令。 |
| **明确不剥的** | `direnv exec` `devbox run` `mise exec` `npx` `docker exec`。理由写得很直白：它们把参数当命令执行，所以 `Bash(devbox run *)` 会连 `devbox run rm -rf .` 一起放行。 |
| 某些包装不能靠前缀批准 | `watch` `setsid` `ionice` `flock`，以及带 `-exec` / `-delete` 的 `find`。 |
| 环境变量前缀的不对称 | 允许规则只跨过已知安全的变量赋值；拒绝规则跨过**任意**赋值——所以 `Bash(rm *)` 在拒绝列表里仍然命中 `FOO=bar rm -rf tmp/`。**放行要严，拦截要宽。** |
| 没加引号的通配符 | 只读命令带通配符一般放行（`ls *.ts`），但 `find` `sort` `sed` `git` 这类带有写 / 执行能力开关的命令要问——**因为通配符可能展开成一个 flag**（目录里正好有个叫 `-delete` 的文件）。 |
| `cd` 与 `git` 同一段要问 | 换了目录再跑 git，会执行*那个目录的* git 钩子——等于执行别人的脚本。 |
| 重定向按文件写检查 | `> 文件` 走和编辑工具一样的边界检查；`/dev/null` 不查；目标以 `~` 开头或含通配符要批准。 |
| 超过 1 万字符一律问 | 超出解析器的处理范围了，那就别装作看懂了。 |

这份规范最诚实的一句在结尾：**试图靠模式约束命令参数是脆弱的**，并用 `curl` 举了五种绕法。它推荐的替代方案是整条 deny 掉、改走按域名放行的抓取工具，或者干脆用钩子自己校验。

### 它的「屋子」是什么样的

证据里没有核到进程级沙箱。它的隔离面是执行护栏，性质上更接近「行为约定」而不是「锁」：

- `cd` 只在项目目录或显式加进来的目录内对后续命令生效，**出界自动重置**，子智能体从不继承
- 默认超时 2 分钟、上限 10 分钟，而且**超时不是杀掉，是转后台**（例外：`sleep` 开头的、跑 `git` 的、解析不了的复合命令，这三类到点停）
- 输出有上限，超了给文件路径和预览，让模型自己去读
- Linux/WSL 上可以给所有 bash 与 PowerShell 命令合起来设一个内存上限（cgroup）

网络控制落在**工具层而不是进程层**：网页抓取按域名规则放行，文档直接建议 deny 掉 `curl` / `wget`。

### 两条与命令无关、但同属攻击面的实现细节

这两条来自 SDK 源码，很能说明「权限校验」的边界比想象中宽：

- 恢复会话的参数必须写成 `--flag=value` 这种单个 token 的形式。理由：这个 flag 的值是可选的，写成两个 token 时，**一个以短横线开头的值不会绑定到该 flag，而会被当成另一个命令行参数**——不可信的值因此能注入任意参数。等号形式永远绑定。
- Windows 专项：拒绝 `.bat` / `.cmd` 形态的可执行路径，并拒绝含有 cmd.exe 元字符（`& | < > ^ % ! "`）的参数值。理由是 Windows 的参数拼接只会给含空白的参数加引号，不含空白的参数里这些字符会原样到达命令行。

#### 顺带一提：它也有模型裁决者

权限模式一共六档，其中默认的自动档是「分类器在后台审」——和 codex 的 Guardian 是同一类东西。另外在审批框上按一个快捷键，可以现场让模型解释这条命令在干什么、为什么要跑、可能出什么事，并标一个风险等级；**这次请求只在你按下时才发出**，不是每次弹框都白花一次 token。

## 不判命令，只如实报出「管住了多少」

<Badge type="info" text="06 · DeepSeek Harness" />

::: info 一句话
dsh 把答法 B 做到了底：**一条命令都不判**。所有命令直接进沙箱跑，撞墙了返回一个标记，模型可以带着理由申请更宽的模式重试一次——**那次重试才弹审批框**。它最独特的贡献不是这个，而是让沙箱**如实交代自己管住了多少**。
:::

### 沙箱接缝只有一个方法

```text
confine(argv, policy) → ConfinedArgv | 抛出 SandboxUnavailableError
```

注意这里没有第三种可能：**「悄悄地不加约束直接放行」永远不合法**。要么给你一个被包好的命令，要么明确抛错说这台机器上没有可用的沙箱。后端有三份：Linux 的 bubblewrap + Landlock（自研的原生扩展）、macOS 的 Seatbelt、Windows 的 ACL 受限令牌。模式同样三档，其中最松的那档**根本不会调用这个方法**——不上锁就不假装上锁。

### 返回值里的四样东西

| 字段 | 是什么 | 为什么要有 |
| --- | --- | --- |
| `argv` | 被包装过的命令数组 | 前面加上了 runner、配置文件、分隔符，然后才是你原来的命令 |
| **`enforcement`** | `full` 或 `partial` | **这台机器上到底管住了这个模式承诺的全部，还是只管住了一个子集** |
| `denialSignatures` | 这个后端的「拒绝方言」 | bwrap 的只读绑定产生 EROFS，Landlock 产生 EACCES，Seatbelt 产生 EPERM |
| `runnerFailureRules` | 「沙箱工具自己挂了」的证据规则 | 用来和上面那条区分开 |

::: info 打个比方
`enforcement: partial` 就是保安老老实实告诉你：「后院那扇门的锁我这把钥匙管不住。」——他没有假装锁上了。

需要绝对保证的调用方看到 `partial` 时，必须**要么拒绝执行、要么把这个差别摆到人面前**，不许当它是 `full`。目前的 partial 情形是：较老的 Landlock 内核版本、Windows ACL 的 Everyone 组、以及硬链接边界。
:::

#### 「命令失败」和「被挡住」是两句完全不同的话

这是三家里只有 dsh 明确做了的区分。源码注释说得很清楚：**runner 失败意味着命令*根本没跑*，而拒绝意味着约束正常工作并挡住了它**。使用方必须**先查 runner 失败，再查拒绝**。还有一条特别提醒：不要拿「所有后端的拒绝特征并集」去匹配，因为并集会声称某个后端根本不会产生的拒绝。

判定 runner 失败的顺序也是写死的：先按允许的退出码门控，再按「信息性输出行」做整行的、大小写不敏感的精确排除，最后才在剩下的错误输出里找致命特征。一句话总结：**退出状态本身永远不能证明 runner 失败了。**

#### 策略是每次调用带的，不是钉在后端上的

每次 `confine` 都要带上模式、工作区根目录和会话 ID。注释给的理由很硬：同一瞬间可能有两个调用方需要不同的边界（bash 跑在只读档，而某个受限的子智能体需要它的状态目录可写），而且——**一次被批准的升级重试，本身就是一个更宽策略的新调用。**

还有一个容易忽略的细节：工作区根目录**先按文件系统语义解析（解开符号链接），再做字符串规范化**。这样当前目录里含 `symlink/..` 时，识别到的是子进程*实际运行*的那个目录，而不是字符串看起来的那个。

### bash 的审批由沙箱触发，不由命令内容触发

逐行读过它的 bash 工具确认：**没有命令白名单、没有词法器、没有风险分档**。被拒时返回一个标记 `[sandbox: file access denied under <mode> mode]`，模型可以用**完全相同的命令**加上一个更宽的模式申请和一句理由重试。

它写给模型的规矩本身就是一份很好的说明书：

- 尝试一条沙箱可能拒绝的命令是**安全且预期的**：跑它、读标记，不要预先假设会被拒
- 被拒且更宽的模式能让它成功时，**同一轮内立刻升级**——这是对一次拒绝唯一被许可的例外
- 不要绕道去聊天里先要权限，**那次重试弹出的审批框就是用户同意的方式**
- 绝不投机性升级：请求必须建立在一次**真实的**拒绝上
- 会话若声明审批框已禁用，拒绝就是终局
- 一次被拒的升级对那条命令是终局，停下解释，绝不绕过

### 审批：封闭四值，只有一个放行

| 取值 | 含义 |
| --- | --- |
| `allowed-once` | <Badge type="tip" text="放行" />——而且只放这一次，没有「本会话都批」这个选项 |
| `rejected` | <Badge type="danger" text="拦住" />——人明确说了不 |
| `cancelled` | <Badge type="danger" text="拦住" />——被取消了 |
| `unavailable` | <Badge type="danger" text="拦住" />——**没人应答、答复者不是属主、抛错、返回了不合规的值，全部归到这里** |

最后一行是重点：**所有的意外都倒向拒绝，不倒向开闸**。会话策略只有两档——询问，或者永不询问（用于 CI 与无人值守，确定性地返回拒绝）。而且「永不询问」**在服务内部先于瀑布生效**，所以后来插队注册一个答复者也绕不过它。

#### 两条形状上的讲究

- **审计必须成对**。提出审批请求要求会话正处在一个打开的回合里，因为「请求」与「答复」这一对审计记录必须被日志的提交边界括住。任何一半写失败，整个请求就作废——**「返回一个没有记录的决定」被判为违约。**
- **审批请求刻意不带工具参数**。它只带调用 ID，答复者靠这个 ID 把提示挂到*已经在界面上流式呈现过的那次调用*上，「而不是再渲染一份可能漂移的副本」。前面那个「先落日志再执行」的顺序，就是为了让这一条永远成立。

与之配套的是另一条硬规定：**审批阶段不许改写工具参数**。注释原话是「参数已经落日志、已经展示过了」——改写会让历史、审计、界面、执行四者对不上。这一条恰好和 Claude Code 相反，见[下一节](#conflict)。

最后一个小设计值得记：它把「沙箱模式」和「审批策略」两个旋钮**打包**成一个权限选择器，默认只给两项——工作区可写 + 询问，或者完全放开 + 从不询问。codex 让你分别调两个旋钮，dsh 认为普通人只需要在两个套餐里选一个。

## 它们在这三件事上互相矛盾

<Badge type="info" text="08 · 三处硬分歧" />

下面三处不是「谁做得更全」的差别，是**同一道题的相反答案**。两条路各自都自洽，但混着走一定出问题——所以如果你在设计自己的系统，这三处必须选边。

### 分歧一：审批的时候，能不能改写工具参数？

::: claude 可以 |
批准的回答里可以带一份改写过的入参（不给就回填原来的）。好处是人可以在放行前顺手把参数收窄——比如把删除范围改小一点。

代价：界面上展示的那份和真正执行的那份可能不是同一份，所以改了必须重新呈现。
:::

::: dsh 明确不许 |
类型上就排除了这个可能，注释原话：**参数已经落日志、已经展示过了**。改写会让历史、审计、界面、执行四者对不上。

代价：人只能整体批或整体驳，没有「批一个收窄版」这个中间选项。
:::

### 分歧二：模型能不能当裁决者？

::: info Codex / Claude Code：能
codex 有一个独立的审查会话，拿到压缩过的对话上下文去评估这一次的具体动作，要求返回严格 JSON，**超时或输出不合法一律按拒绝处理**。Claude Code 的自动档是后台分类器。

好处：能判「意图」，而不只是命令字面——比如「这个载荷是从敏感数据派生来的」。
:::

::: dsh 不能 |
它的答复者链只面向人。这与它的整体选择是自洽的：**一家连命令内容都不判的系统，自然也不需要一个判意图的模型。**

它把这份判断力全部交给了沙箱和人。
:::

### 分歧三：规则住在哪里？

::: codex 外置的策略文件 |
可以 review、可以进版本库、可以随仓库分发、自带用例、有单独的测试命令。管理员能强制下发，用户改不动。

**这是唯一一种在多租户场景下站得住的形状**——「这个租户允许跑什么」必须是一份可审计的配置。
:::

::: claude 配置文件 + 增量写入 |
分层配置里的规则，由你每次点「不再询问」增量写进去。单人本地非常顺手。

问题在于：几个月后没人说得清那一行是*什么时候、因为什么*被批准的。DeepSeek Harness 则一条规则都没有。
:::

## 三家独立撞出的同一个答案

<Badge type="info" text="09 · 四条共识" />

分歧之外，有四件事三家的做法在形式上完全不同、性质上完全一致。**同一个答案被三次独立发明，通常意味着它是对的。**

::: info 拒绝路径优先于批准路径 — 同题三解
Claude Code 用固定定序（拒绝在允许之前），dsh 用只能收紧的守卫，codex 用「多条规则命中取最严」。三种写法，一件事。
:::

::: info 不确定时倒向拒绝 — fail closed
codex：包装嵌套超过 8 层直接判危险、审查员超时按拒绝、没有沙箱就不自动批。dsh：没人应答不算放行。Claude Code：拒绝规则在最松的模式下也生效。
:::

::: info 批准这个动作可以顺手改策略 — 三家都有，名字不同
差别只在「写到哪一层配置、活多久」。最窄的一档是「本会话不再询问」，最宽的是「写进项目配置并提交进版本库」。
:::

::: info 升级重试比事前判准更值钱 — codex 与 dsh 的共同下注
两家都把「判错的代价」从「挡住了本该放行的事」降成了「多跑一次」。区别只在谁发起重试：codex 是编排器自动发起，dsh 是模型带着理由发起。
:::

## 这轮调查改变了什么

<Badge type="info" text="10 · 落到本仓" />

本仓目前站在**答法 A** 那一档：一个静态命令判定器，加工作目录约束、超时和输出截断。这个选择当初是在「没有沙箱」这个前提下做的，而下面六条是这轮对照带回来的具体动作项。

1. **OS 沙箱不是替换判定器，是给它兜底**。两家独立证明这一档不需要容器基建。它的意义在于**把判定器从「唯一防线」降级成「误伤过滤器」**——判定器仍然有用，但它漏掉的那一条不再直接就是越界。
2. **那张「永远不许进白名单」的表，本仓还没有**。既然允许按命令签名永久放行，「哪些签名永远不许进白名单」就是一个必须回答的问题。codex 已经把答案写成了 88 条前缀（`core/src/exec_policy.rs:56-145`）。
3. **把「护栏不是沙箱」从文档口号变成运行时分支**。照抄 codex 那个 `match get_platform_sandbox()` 的形状：没有可用沙箱时，本来能自动批的操作要退回去问人。
4. **「命令自己失败了」和「被护栏挡住了」在界面上要是两句不同的话**。dsh 证明了做这个区分需要什么：后端自报的拒绝方言，而且不能拿跨后端的并集去匹配。
5. **审批端口不能既是策略又是兜底**。Claude Code 的六步定序给出的答案是把两者分开：规则是策略，钩子是穿透一切的拦截点。否则会撞上那个典型失效模式——你以为你的回调在把关，实际上它被上游的允许规则短路了。
6. **「审批框看到的参数」与「实际执行的参数」是不是同一份，要选边**。dsh 的「参数只有一份：先落日志、先展示、不许改」比「让审批通道单独再取一次参数」更彻底。
