# 别动前缀

<Badge type="info" text="三家对读 · 第十七份" />

提示词缓存是**前缀精确匹配**：前面变一个字节，后面全部重算。这一条硬约束反过来决定了四家的提示词装配长什么样——谁能往里写、按什么顺序、变了之后怎么告诉模型。九个维度里有一个是*四家独立走到同一个答案*的。

<Badge type="warning" text="Claude Code 2.1.246" /> <Badge type="tip" text="codex（Rust 全量）" /> <Badge type="info" text="deepseek-harness（TS 全量）" /> <Badge type="info" text="本仓 §5.4 / §9.3" />

核验日期 2026-08-27 · 结论只进 evidence，不直接进架构正文

## 这件事在解决什么

一次模型请求不是一段字符串，是十几个来源拼出来的东西：harness 自己的身份、部署方的人格、每把工具的用法、项目里的 `AGENTS.md`、当前权限档、仓库结构、检索回来的片段、这一轮的对话。谁负责拼、按什么顺序拼，看上去是个纯工程问题。

**缓存把它变成了架构问题**。三家 provider 的提示词缓存都是前缀匹配——从头开始逐字节比对，遇到第一个不同就停，前面的算命中，后面的全部重算。于是「把当前时间写进系统提示词」这种事的代价不是多几个 token，是*每一轮都全价重来*。

这条约束逼出四个真问题，四家各自作答：

- **谁能往系统提示词里写**？如果任何插件都能追加一段，那前缀就由最不稳定的那个插件决定。
- **会变的东西放哪**？权限档、当前时间、工具目录——它们必须被模型看见，又不能进前缀。
- **变了之后怎么说**？历史是只追加的。旧的那段还躺在上面，模型会读到两份互相矛盾的状态。
- **怎么知道缓存被打破了**？失效是静默的——账单涨了，功能一切正常。

::: info
这份是这个系列里**第一次**写提示词装配。前面十六份里，「上下文管理」那份写的是*压缩*（什么时候压、在哪一步压、摘要写成什么样），与本份不重叠：压缩处理的是「装满了怎么办」，本份处理的是「一开始怎么装进去的」。
:::

## 九个维度

按一段文字进入请求的路径排：先是谁有资格写、写在哪、算静态还是动态，然后是它变了之后怎么办、怎么被认出来，最后是整条前缀什么时候碎掉、怎么发现。

### 01 谁有资格往系统提示词里写 <Badge type="warning" text="分岔" />

如果任何插件都能追加一段，前缀就由最不稳定的那个插件决定。四家都不允许这样，但拦的方式完全不同。

- **Claude Code**：按**层**拦：系统提示词层只有核心指令、工具定义、输出风格。hooks 的 `additionalContext`、skill 正文、plan 模式指令一律追加成对话消息。
- **codex**：按**类型**拦：实现 `WorldStateSection` trait 才算数，17 个 section 编译期确定，各占一个文件。
- **deepseek-harness**：按**注册表**拦：`ctx.systemPrompt.section({name, order, text})`，插件都能贡献，但名字唯一、重名直接抛。
- **本仓**：按**通道**拦：两条不同的接口。`ContextSource` 搬材料、产出**落不到 `system`**；`InstructionSource` 是可信指令，**只由 composition root 注册**。

本仓这条是四家里唯一在**类型上**把「材料」与「指令」分开的。ADR-0014 的理由不是缓存，是权威：普通 source 搬运的是给模型看的材料，而项目规则是「可信但低于平台」的指令，需要一个结构性的权威位置——让它们共用一条通道，等于让任何一个检索插件都能产出一段看起来像规则的文字。缓存收益是顺带的。

::: tip 判断
dsh 是四家里最开放的：任何插件都能注册一节。它靠三样兜住——名字全局唯一、`order` 有约定表、以及一个包级 `invariant` 在每次装配之后校验结果（名字非空、不重复、text 是字符串、变量名合法）。**开放 + 运行期校验**，而不是关闭。
:::

还有一个只有 dsh 有的旋钮：`PromptSection` 可以带 `complete: true`，宣称「我就是完整的系统提示词」。装配仍然跑完整个协作瀑布（好让工具、上下文、变量都被解析），然后把这一节恢复成唯一的提示词节；出现两个有效的 `complete` 节则装配失败。这是给「我要完全接管提示词」这个需求留的门，而且是*带失败模式*的门。

### 02 顺序谁定，生产者知不知道自己在哪 <Badge type="warning" text="分岔" />

缓存是前缀匹配，所以「谁排在前面」直接决定「谁变了会连累谁」。

- **Claude Code**：三层固定，按「**多久变一次**」排：系统提示词 → 项目上下文 → 对话。
- **codex**：section 的注册顺序，但 **ID 要持久化进 rollout**，所以必须保持稳定——顺序成了一条兼容性约束。
- **deepseek-harness**：`order` 数字升序，带一张约定表：`-100` harness 身份、`0` 部署人格、`100–199` 工具指引。
- **本仓**：**生产者不知道自己在哪**。只声明 `stability`（`run-stable` / `dynamic`），位置由装配器按固定映射决定，插件点投不进来。

::: tip 判断
本仓这条最严，而理由不是洁癖。ADR-0034 写的是：*生产者自报位置会让降级渲染变成一次契约面变更*——某档 profile 不支持中途 `role:"system"`（§9.8），装配器得把 `dynamic` 块换个位置渲染；如果位置是生产者声明的，这个降级就得改所有生产者的声明，而那是一次跨包契约变更。**只声明事实、不声明位置**，降级就只是装配器内部的事。
:::

dsh 那张约定表值得抄的是它的**负数区**：`-100` 给 harness 自己的身份，`0` 给部署方的人格，中间留白。这样部署方写自己的人格时不必知道 harness 用了哪些数字，而 harness 加新的身份段也不会挤到部署方前面去。

codex 把顺序绑进了持久化：section ID 写进 rollout 文件，恢复一个旧会话时要按 ID 对上。代价是**改名等于破坏兼容**，收益是差分能跨会话恢复继续算（见维度 4）。

### 03 会变的东西放哪 <Badge type="tip" text="四家独立同构 · 可当定论" />

权限档、当前时间、工具目录——必须让模型看见，又不能进前缀。放哪？

- **Claude Code**：追加成**对话消息**。文档原话：plan 模式与 skill 加载「把指令作为对话消息追加，所以缓存前缀保持完整」。
- **codex**：片段渲染成 `ResponseItem::Message`，分类挂在 metadata 上随消息走。**注入的是消息，不改系统提示词。**
- **deepseek-harness**：`PromptContext`——类型注释原文称它是 `the cache-safe counterpart to PromptSection`，落成保留历史之后的一条 user 角色快照。
- **本仓**：`dynamic` 块进 messages 末尾的 `role:"system"`；§9.3 ③ 明写「会话中途的运行时指令追加到 messages 末尾，而不是改顶层 system」。

**这是整个系列里证据最硬的一次同构**。四份代码库互不相通，四个团队各自把它写进了自己的类型注释与架构文档，用的还是不同的词（「对话消息」/「片段」/「cache-safe counterpart」/「dynamic 块」），指的是同一件事：*动态内容一律追加，永不回头改前缀*。

dsh 把它的后果说得最直白。审批策略那一节的原文：

> Both policies contribute their complete current meaning to the cache-safe runtime-context snapshot. … changing approval state appends a new full snapshot after retained history without rewriting the request header's system prompt.

也就是说，**用户切一次权限档不会废掉整条提示词缓存**——这在一个交互式 CLI 里是每分钟都可能发生的操作。如果权限状态写在系统提示词里，每次切档都要全价重算整条历史。

### 04 它变了：整份重发，还是只发差分 <Badge type="warning" text="分岔 · 三比一" />

既然只能追加，那权限档从 `ask` 变成 `never` 的时候，是把整份状态再贴一遍，还是只说变了的那一处？

- **Claude Code**：整份追加。
- **codex**：**差分**。每个 section 实现 `snapshot()` + `render_diff(previous)`，没变就*什么都不产出*。
- **deepseek-harness**：整份追加，且是有意的——原文 `appends a new full snapshot`。
- **本仓**：整份重装：每个 Step 重新求值 `dynamic` 块。

codex 是唯一付了差分成本的，而这个成本相当可观：它需要为每个 section 定义一个**可比较的快照类型**（trait 注释里明写 *Snapshot 只放「决定下一步要告诉模型什么」所需的比较数据*），需要把快照持久化进 rollout，需要处理「上一份快照现在还在不在历史里」。

::: tip 判断
最后那条是差分真正的难点，codex 的答案是一个三态枚举：<br> `Absent`——保留历史里没有这一节，也没有持久化快照 → **重新全量注入**；<br> `Unknown`——历史里有这一节，但拿不到它的类型化快照（比如旧格式）→ 按未知处理；<br> `Known(&T)`——拿到了确切的快照，可以真的算差分。<br> 压缩把旧片段裁掉之后，下一步自动落进 `Absent` 分支补回全量。*差分机制必须先能回答「我上次说的那句话还在不在」*，否则模型会收到一句「权限从 X 变成了 Y」而根本没见过 X。
:::

另外三家用「整份重发」绕开了这整套机器。代价是 token：每次权限变化贴一份完整状态。收益是**没有状态机**——不需要快照类型、不需要持久化、不需要三态判定，也不会出现「差分算错了导致模型看到一个不存在的中间状态」这类 bug。

### 05 怎么在历史里认出自己上次注入的那一段 <Badge type="warning" text="分岔" />

这是维度 4 的前提。纯拼字符串写进去就认不出来了——它和用户自己打的字长得一模一样。

- **Claude Code**：未核到。已知的是注入内容有 `<system-reminder>` 这类标记包裹，但匹配机制没读到。
- **codex**：**三件套**：`markers()` 起止标记 + `content_kind()` 稳定分类（`<feature>.<name>`）+ `matches_retained_fragment()` 反向识别。另有 SHA1 指纹。
- **deepseek-harness**：靠 `name` 唯一 + 日志重放：模型历史由 `deriveMessages()` 从会话日志投影出来，快照本身就是日志里的一条。
- **本仓**：`ContextManifest` 落库，是「那次选择的证据」（ADR-0038）——但它的用途是**事后可查**，不是在历史里再认出来。

codex 的 `ContextualUserFragment` trait 注释把这一步的意义写清楚了：*标记让历史里的注入内容可被机器识别，从而可以在下一轮被替换、被跳过、被差分*。没有标记的片段（`markers()` 返回两个空串）只渲染正文，并且注释明写它**永远不会匹配到任意文本**——这是防止空标记退化成「匹配一切」。

::: tip 判断
那个 SHA1 指纹的三个细节都是踩过坑的样子：<br> ① 先喂一个域分隔串 `codex-world-state-fragment-v1\0`——版本化，将来换算法不会撞老哈希；<br> ② 每段内容先把 `\r\n` 归一成 `\n` 再算——**换行符不该让指纹变化**；<br> ③ 每段内容前面塞它的长度——防止 `("ab","c")` 与 `("a","bc")` 算出同一个哈希。<br> 三条都是「这个哈希会被用来判断相等」才需要的讲究。
:::

dsh 走的是完全不同的路：它不需要在*文本*里认，因为模型历史本来就是从结构化日志投影出来的——快照是日志里一条有名字的事件，投影时按名字取最后一条即可。**把「历史」定义成日志的投影而不是一个字符串数组，这个问题就不存在了。**

### 06 工具目录变了算不算动前缀 <Badge type="tip" text="认定同构 · 做法分岔" />

工具定义在前缀里。那「按需装载工具」这件事，天生和缓存对着干。

- **Claude Code**：工具定义属**系统提示词层**，一变废掉整条缓存——所以 tool search 的延迟加载工具**只追加不动前缀**。这是那套设计的理由，不是副作用。
- **codex**：延迟加载的命名空间做成 `ToolsState` 世界状态节，走差分片段：4KB 上限，每个命名空间描述截到 250 字符。
- **deepseek-harness**：`ToolProviderResult` 给两份：`schemas` 是本次装配的可见集，`knownNames` 是**限制前的名字全集**。
- **本仓**：§9.3 ② 直接禁掉：「工具列表确定性序列化，按 name 排序，工具集不许在会话中途增删」。这也是 §9.5 建议按 Agent **静态裁剪**而非运行时动态加载的理由之一。

四家在**事实认定**上完全一致：工具定义在前缀里，动它就废缓存。分岔在「那还要不要按需装载」——本仓选择不装载（静态裁剪），另外三家选择装载但*把装载这件事本身移到断点之下*。

::: tip 判断
Claude Code 的做法与本份的主线咬得最紧：模型拿到的是一份工具**摘要**，需要能力时去搜，装上之后后续轮次一直可用。关键是*装上的是指针不是 schema*——延迟加载的工具变化只追加，不动前缀；而前置加载的工具一变就废掉整条缓存。核心内置工具（Bash / Read / Edit）永远前置加载、不计入阈值——**它们是前缀的一部分，本来就不该动。**
:::

dsh 那对 `schemas` / `knownNames` 解的是另一个问题，但值得记：`knownNames` 的用途是区分「配置里把工具名写错了」与「这个工具在这个作用域被刻意藏了」。两种情况在「模型看不到这把工具」这个结果上一模一样，而一个是 bug、一个是设计。*把限制前的全集也交出来，这个区分才做得出来。*

### 07 跑到一半改了项目规则，这一轮生不生效 <Badge type="warning" text="分岔 · 这是纪律的直接代价" />

用户在编辑器里改了 `CLAUDE.md`。系统提示词里那份是旧的。重读它 = 动前缀。

- **Claude Code**：**不失效，但也不生效**。文档逐条写明：中途改 CLAUDE.md 缓存不失效，改动要等下次 `/clear` 或重启才加载。改输出风格同理。
- **codex**：**生效，且不动前缀。**`AgentsMdState` 是 17 节世界状态之一，变了就发一个差分片段追加到断点之下。
- **deepseek-harness**：看放哪：`PromptSection` 的 text 可以是每次装配求值的函数（生效但动前缀），放 `PromptContext` 则生效且不动前缀。**取舍交给注册方。**
- **本仓**：**不生效，且是明写的决定**。可信指令由循环在 *Run 起点采集一次*，逐 Step 递进装配器。

::: tip 判断
本仓 ADR-0034 给的理由，与 Claude Code 的行为是同一个：*每个 Step 重读一遍的话，Run 跑到一半规则文件被改，顶层 `system` 就跟着变了*。两家独立选择了「宁可不生效，也不让前缀在 Run 中途漂移」。本仓还多一句：这也是根规则「Run 内恒定」的实现方式——**它同时是缓存决定和语义决定**，规则在一个 Run 里必须是一份，不能前三步一份后三步另一份。
:::

codex 用差分买到了第三种答案：既生效，又不动前缀。而它为此付的代价在这一节里露出来了——托管指令换新的时候，追加的片段带一句**显式作废声明**：

> These managed developer instructions replace all previously provided managed developer instructions.

这一句是「只追加、永不改写」这条纪律的账单：**旧的那段还躺在历史里**，模型会读到它。所以新的那段必须自己带上一句「上面那些作废了」。同一个文件里还有一条 `REMOVAL_NOTICE`——策略被撤销时也得说一声，因为「什么都不说」在只追加的历史里等于「旧的还算数」。

顺带一条上限：托管指令有 `MAX_MANAGED_DEVELOPER_INSTRUCTIONS_TOKENS = 10_000`，而且校验时**预先把作废声明那句的长度也算进去**——免得一份刚好卡在上限的指令，在需要发替换通告时反而超了。

### 08 装配失败了怎么办 <Badge type="warning" text="分岔 · 兜底在三个不同的层" />

检索超时、规则文件读不到、某一节产出了非法内容——这一轮还发不发？

- **Claude Code**：hook 侧有明确语义：退出码 `2` 是阻断，其它非零是非阻断错误、动作照常。装配自身的失败路径未核到。
- **codex**：在**单节内容**上兜：托管指令超 10,000 token 直接报错拒绝，工具节渲染超 4KB 就截并留一行说明。
- **deepseek-harness**：在**装配结果**上兜：独立的 invariant 包裹装配瀑布，校验名字非空/不重复/text 是字符串/变量名合法。变量插值是**严格**的——未注册、格式错、有名无值，三种都抛。
- **本仓**：在**来源**上兜，且分两类：可信指令读不到就**抛**；可选 source 收集失败只降级它自己，装配照常返回。

::: tip 判断
本仓那条分类的理由是四家里说得最清楚的：*「规则在那儿却没生效」是「以为设了其实没设」，必须出声*。而 RepoMap、检索、Git 历史这类可选材料收不上来，只是这一轮少了点上下文，不该把整个 Run 拖死。同一个「读失败」，因为**失败的后果不同**而分到两条路上。
:::

还有一个只有本仓做的区分：`degraded` 与 `manifest` **并存不是重复**。证据（manifest）里只放封闭理由码 `source_degraded`，而事件还要说出错误名（`ENOENT` / `AbortError`）——后者是给人当场排查用的，不是那次选择决定的一部分。*同一件事的两个读者要的不是同一份信息。*

取消是本仓的一个例外：`ctx.signal` 已中止时原样抛，不当降级处理。理由很实在——把取消咽成降级，循环会接着去调一次模型。

dsh 的严格变量插值值得单说：<span v-pre>`{{variable}}`</span> 引用未注册的名字会抛、格式不完整会抛、注册了但这次装配没有值也会抛。错误信息还会把当前已注册的变量名全列出来。这是把「提示词里有个占位符没被替换」从一个**模型才能发现的问题**变成一个**装配期就报错的问题**。

### 09 前缀什么时候碎掉，以及怎么发现 <Badge type="warning" text="分岔" />

缓存失效是静默的：账单涨了，功能一切正常，没有任何报错。

- **Claude Code**：**逐条列了一张清单**。失效：换模型 · 换 effort · fast 模式 · MCP server 连断 · 开关 plugin · deny 掉一个工具 · 压缩 · 升级。不失效：改仓库文件 · 换权限模式 · 调用 skill · `/rewind`。
- **codex**：未核到失效清单。它的机制隐含答案：世界状态节不变就不产出片段，前缀自然稳。
- **deepseek-harness**：没有清单，但把最高频的那条**刻意做成不失效**：权限档切换追加快照而不重写请求头。
- **本仓**：§9.3 ④：**必须监控 `usage.cache_read_input_tokens`**，长期为 0 说明有静默失效源。四家里唯一把「怎么发现」写成纪律的。

Claude Code 那份清单里有两条特别值钱。**第一条：`/rewind` 不失效**。它把对话截断回更早一轮，而那个前缀本来就在缓存里——所以*回退比压缩便宜*：压缩要造一个新前缀，回退是回到一个旧的。这条把「压缩」和「回退」的成本关系倒过来了，值得在设计撤销机制时记住。

::: tip 判断
**第二条：整条 deny 掉一个工具会失效缓存**。裸工具名 deny 会把它从上下文里摘掉，而工具定义属于系统提示词层。也就是说，一个看起来纯粹是权限操作的动作，实际后果是废掉整条缓存——这正是 §9.3 ④ 那条监控纪律要抓的东西：*没人会预期「改个权限」要重算历史*。
:::

还有一条缓存作用域的事实，Claude Code 侧核到了：系统提示词里嵌了工作目录、平台、shell、OS 版本，所以**不同目录的两个会话互不命中，同一仓库的不同 worktree 也不命中**；同目录并行的会话彼此命中；顺序会话还要启动时的 git 状态快照一致才命中。TTL 方面订阅档自动要 1 小时，API key 与第三方 provider 默认 5 分钟。另外三家这一格没核到。

## 对本仓意味着什么

### §9.3 那三条纪律，被三家独立验证了 <Badge type="tip" text="同构 · 可当定论" />

§9.3 ①（system prompt 冻结）、③（中途指令追加到 messages 末尾）、②（工具集不许中途增删）——这三条当初是自己推的。这一轮对读之后：**③ 是四家独立同构**，用词不同、机制不同、结论一字不差；**② 是四家事实认定一致**（工具定义在前缀里），只在「那还要不要按需装载」上分岔；① 由 Claude Code 的失效清单反向印证（它把工作目录、平台、OS 嵌进系统提示词的代价，就是不同 worktree 之间互不命中）。

**ADR-0034 那条「生产者只声明事实、不声明位置」也被印证了一半**。本仓的理由是「自报位置会让降级渲染变成契约面变更」；dsh 走的是相反的路（注册方自选放 `PromptSection` 还是 `PromptContext`），而它的代价正好显形在维度 7：*同一个「项目规则变了」的问题，在 dsh 那里没有统一答案，取决于注册方当初选了哪个类型。*

### 两条，一条便宜一条贵 <Badge type="warning" text="本仓没有 · 补不补是决策" />

**便宜的：一份失效清单**。Claude Code 把「什么会废掉缓存、什么不会」逐条写进了文档。本仓有 §9.3 ④ 的监控纪律（四家里唯一），但那是*事后发现*；清单是*事前避免*。两者互补而不重复——监控告诉你「有东西在漏」，清单告诉你「大概是哪几个」。本仓现在的失效源可以直接列：换 profile、工具集变化、可信指令重采、压缩。写下来是纯收益。

**贵的：在历史里认出自己注入过的片段**。本仓的 `ContextManifest` 回答的是「那次选了什么」，不是「那段文字现在还在不在历史里」。没有这个能力，维度 4 的差分就无从谈起——而差分是「既让规则中途生效、又不动前缀」的唯一已知解法。要不要走这条路取决于「Run 内恒定」这条根规则要不要松动：*如果它不松动，差分就没有用武之地，这条缺口可以一直空着。*

### 一个真问题：装配器要不要开放给插件 <Badge type="warning" text="三家分歧 · 得自己判" />

本仓现在是四家里最封闭的：`InstructionSource` 只由 composition root 注册，`ContextSource` 的产出**在类型上**落不到 `system`。dsh 是最开放的：任何插件都能注册一节系统提示词，靠名字唯一 + 运行期 invariant 兜住。codex 在中间：编译期确定，但每节是独立文件、有自己的测试。

这个分歧到 M2 会变成真问题——企业端 pack 要不要能贡献自己的提示词节？现在的答案是「经 composition root」，那在单体装配里成立；一旦出现「部署方自己加一段人格」这类需求，dsh 那套**开放注册 + 约定 order 表 + 运行期校验**是现成的形状，而它的 `-100 / 0 / 100–199` 分区法解的正是「harness 与部署方各写各的、互不挤占」。

## 证据档次与明确没核到的

codex 与 dsh 是全量源码，常量与类型注释直接读到定义处。**Claude Code 这一列是本份里最弱的**——三层排序、失效清单、缓存作用域、TTL 都来自官方文档（逐条列明，可当事实），但机制层读不到。

- **Claude Code 的断点怎么打：没核到**。二进制里 `cache_control: {type:"ephemeral"}` 有命中，但上下文看着像内嵌的 API 参考文本，不是它自己的调用点。所以我只说「三层排序」，没说「三个断点」。
