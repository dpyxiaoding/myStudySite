# 上下文管理：三家差异

本篇把 Claude Code、codex、deepseek-harness（下文简称 dsh）的上下文管理放在一起比较。小节和三家各自的页面一一对应，每节先列对照表，再说哪里一样、哪里不一样、为什么。各家的细节和出处在各自的页面里，每节末尾有链接。

::: info 依据
- 和三家页面用的是同一批资料：Claude Code 2.1.296，codex rust-v0.162.1（源码提交 `8c0f701`），dsh 0.2.1-alpha.2（源码提交 `d743267`），2026-10-11 核对。
- 证据的分量不一样：codex 和 dsh 读的是源码，Claude Code 引擎不公开，依据是官方文档。表里 Claude Code 写「文档没写」的格子，不代表它没有这个机制。
- 三家页面里没写、本篇另外核的几处，列在文末「来源」里。
:::

## 一句话

三家对「上下文是什么」的看法不同，后面的大部分差异都从这里来：

| | 把上下文看成 | 所以 |
| --- | --- | --- |
| Claude Code | 一串要保护的缓存前缀 | 每个设计先问会不会弄脏前缀：会变的信息追加在后面，暂时用不上的工具也不删，压缩时摘要请求复用对话的前缀 |
| codex | 一个可以整个换掉的窗口 | 压缩就是开一个新窗口，只带用户说过的话和压缩结果过去，背景按当前状态重新装一遍 |
| dsh | 只追加的事件日志上的一层投影 | 压缩不删任何东西，只追加一条摘要把一段遮住；压缩的每一步都记成事件 |

这三种看法并不互斥，三家在不少地方做法相同；看法决定的是各家最有特色的那部分设计。

### 三家一样的地方

- **会变的信息追加在后面，不改前面。** 提示词缓存按前缀匹配，改了前面，后面全部要重新计算。三家都把中途的变化写成新消息追加：Claude Code 用 `<system-reminder>`，codex 只追加世界状态里变了的部分，dsh 追加一份新的 `PromptContext` 快照。
- **大输出进入历史之前先限制大小。** 不调模型，只按长度处理，和压缩是两层。
- **压缩用一份摘要代替较早的历史，原始记录留在磁盘上。** 变的只是之后发给模型的内容。
- **压缩请求接在原有对话后面。** 三家都在历史末尾追加一条压缩指令，不另起一个专门做总结的请求。
- **模型默认不能自己压缩。** 压缩由 harness 按阈值触发，或者由人手动触发。模型能做的是少往里放东西：派子代理、分段读、只看需要的部分。

### 三家不一样的地方

- **在多满的时候压**：默认配置下，Claude Code 用 100 万窗口的模型时约在 96.7%，codex 在 90%，dsh 用默认的 DeepSeek 接口时约在 68%。见[怎么知道快满了](#怎么知道快满了)。
- **截掉的输出还能不能取回**：dsh 全文存文件，并告诉模型怎么读；Claude Code 成功的大结果存文件给路径，失败的只留首尾；codex 只留首尾，全文只在模型拿不到的记录文件里。见[单条结果太大怎么办](#单条结果太大怎么办)。
- **压缩时原样留下什么**：Claude Code 和 dsh 留最近的一段原文；codex 只留用户说过的话，模型的回复和工具输出全部交给压缩结果。见[满了怎么压](#满了怎么压)。
- **摘要看不看得到**：codex 默认交给 OpenAI 服务端压缩，结果是加密的；Claude Code 的摘要提示词不公开，但摘要全文可以在钩子里拿到；dsh 的摘要模板和每次的摘要都在日志里。见[满了怎么压](#满了怎么压)。
- **压缩一直不见效时怎么办**：Claude Code 数次数，停下报错；codex 源码注释写明不设防；dsh 要求每次重试前有可测量的进展。见[压坏了怎么办](#压坏了怎么办)。

## 你能看到和操作的

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 手动压缩 | `/compact`，后面可以写希望保留什么 | `/compact`，不能带说明 | `/compact`，不能带参数 |
| 只压一部分 | `/rewind` 里选一条消息，压它之前或之后的部分 | 斜杠命令里没有 | 界面上没有；程序可以调用 `compactRegion` 指定范围 |
| 看用量 | `/context` 按类别列出；状态栏可以一直显示 | 底栏一直显示剩余百分比；`/status` | 输入框下方的圆环，点开是按类别的明细 |
| 长期的压缩要求 | CLAUDE.md 里写一节压缩说明 | `compact_prompt` 整个替换摘要提示词，只对本地摘要有效 | 不能写说明；可以指定另一个模型写摘要 |
| 调阈值 | 设自动压缩窗口（10 万到 100 万 token），或者按百分比调低 | 设 token 数，不超过窗口的 90%；可以改成只算本窗口新长出来的部分 | 比例、余量、保留量都能调，还能按模型分别设 |
| 关自动压缩 | 能，手动 `/compact` 还能用；也能连手动一起关 | 配置参考里没有这一项 | `auto: false` |
| 压缩前后的钩子 | PreCompact、PostCompact、SessionStart（匹配 `compact`） | 同样三个 | 没有，要写插件 |

**钩子：Claude Code 和 codex 几乎一样。** 名字和触发点相同，SessionStart 都用 `compact` 匹配压缩之后的那一次。差别在钩子能拿到什么：Claude Code 的 PreCompact 收到 `/compact` 后面写的说明，PostCompact 收到摘要全文；codex 的两个钩子除了通用字段，只多收到触发方式（`manual` 或 `auto`）和回合 id。codex 默认用服务端压缩，客户端本来也拿不到摘要内容。dsh 的实验包能读这两家的钩子配置，但把 PreCompact、PostCompact 列为不支持。

**对摘要能提多少要求，差别大。** Claude Code 每次压缩都能带一句说明，也能在 CLAUDE.md 里长期写。codex 只能整个替换提示词，而默认的服务端压缩不用这个提示词，所以用 OpenAI 时没有办法影响摘要写什么。dsh 不能写说明，但模板是公开的固定八节。

## 上下文里装了什么

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 历史存成什么 | JSONL 记录，每条用 `parentUuid` 指向上一条，连成一条链 | 内存里是 Responses API 的条目序列，另写一份 JSONL 记录文件 | 只追加的事件日志；发给模型的是日志上的投影，叫 surface |
| 背景信息放在哪 | 系统提示词，加上用户消息里的 `<system-reminder>` | 63 种带开头、结尾标记的片段，分 user 和 developer 两种角色 | `PromptSection` 进系统提示词，`PromptContext` 作为一条消息放在历史后面 |
| 中途变了怎么办 | 追加一条 system reminder | 世界状态分 19 个部分，每轮只追加变了的部分 | `PromptContext` 变了就追加一份完整快照 |
| 暂时用不上的工具定义 | MCP 工具默认只放名字，模型用 ToolSearch 取完整定义 | 模型支持时 MCP 工具同样先不放定义，用 `tool_search` 取；内置模型都支持 | 没找到对应机制 |

**不一样：程序认不认得出历史里的每一段。** codex 和 dsh 在结构上让程序能认出历史里哪段是什么：codex 的每种片段都能反过来匹配历史里的文字，dsh 的每个 surface 节点都对应一条有类型的事件。压缩时 codex 要「把背景按当前状态重新装回去」，dsh 要「背景快照被遮掉了就重新追加」，都靠这一点。Claude Code 压缩后也从磁盘重读 CLAUDE.md、记忆等内容再装回来，内部怎么识别，文档没写。

**一样：原始记录都留着，都不给模型看。** Claude Code 压缩时在 JSONL 里写一条边界记录，重建对话时故意不跟回被压掉的那段；codex 的记录文件里工具输出是完整的，每次压缩写一条 `Compacted` 记录，恢复会话从最近一条开始；dsh 被遮住的事件原样留在日志里，任何一次发给模型的请求都能从日志算出来。三家的原始记录都是给人看和恢复会话用的，默认都不给模型回查。dsh 有一个实验包能做到，见[模型能不能自己管](#模型能不能自己管)。

**工具定义：Claude Code 和 codex 做法相同。** 都是 MCP 工具先只登记，不把完整定义放进请求，模型需要时搜索取出。两家的技能清单也都限了预算：Claude Code 是窗口的 1%，codex 是窗口的 2%、最多 1 万 token。dsh 的工具定义里有 `deferLoading` 标记，但源码里只看到它用在会话中途新增的工具上：新工具标上它，再由后面的一条消息启用，开头的工具清单不用改。这同样是「不改前面」的做法，但不是「先不放、用时再取」。

## 怎么知道快满了

<!--@include: ./figures/context-thresholds.svg-->
<figcaption>三家默认配置下在哪压缩，按同一比例画。Claude Code 取原生 100 万窗口的模型，codex 取内置模型，dsh 取默认的 DeepSeek 接口。dsh 名义上在 80% 压缩，但阈值不能超过「窗口 − 输出预留 − 65,536」，实际在约 67.8 万。</figcaption>

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 默认窗口 | 100 万（Fable 5 系列、Sonnet 5 及以后等）；Opus 4.6、Sonnet 4.6 不选 `[1m]` 时是 20 万 | 27.2 万（内置模型），最多可设到 87.2 万 | 100 万（内置的 DeepSeek 模型） |
| 默认在哪压 | 约 96.7 万 | 24.48 万，窗口的 90% | 678,464，约 68% |
| 怎么算出来 | 文档只给了结果 | 窗口 × 90%；另有窗口 95% 的强制线 | 窗口 × 0.8 和「窗口 − 输出预留 − 65,536」取小的；DeepSeek 接口默认给输出预留 25.6 万 |
| 留出来的空间 | 一块「压缩缓冲」，大小文档没写 | 最后 5% 留给系统提示词、工具和模型输出 | 输出预留，再加 65,536 的余量；摘要的输出上限默认也取这个数 |
| 判断用的用量 | 文档没写 | 上次 API 报告的总数，加上之后新条目的估算（4 字节约 1 token） | 这次请求和上次成功的请求信封完全一致时，用服务商报告的数；否则整份按估算规则重算 |
| 什么时候检查 | 文档没写，只提醒自动压缩可能在任务中途触发 | 回合开始前、回合中每次模型回复后、换模型前 | 每一步发请求前 |
| 给人看的用量 | `/context` 调 API 的计数接口逐类计数；状态栏用上次回复的输入量 | 底栏的百分比，分子分母先各减 1.2 万 token 的基线 | 圆环，点开按类别 |

**比例差得多，是因为留出来的空间不同。** dsh 名义上在 80% 压缩，但默认的 DeepSeek 接口每次请求给输出预留 25.6 万 token，再留 65,536 的余量，「窗口 − 输出预留 − 65,536」只有 678,464，比 80 万小，实际就在这里压。codex 留的是窗口固定的 5%。Claude Code 只公开了压缩点，没公开怎么算。

**codex 可以换计算口径。** 默认按整个上下文算；设成 `body_after_prefix` 后，只算本窗口开头那块之后新长出来的部分，阈值管的就只是对话本身长了多少。另外两家没有对应的选项。

**用量从哪来：都以服务商报告的数为基础，新加的部分靠估算。** codex 直接拿上次回复报告的总数，加上之后新条目的估算。dsh 对「什么时候能信服务商的数」更严格：要求这次请求和上次成功的那次信封完全一样，否则整份重算；它还给出每个节点各占多少，选压缩范围时直接用。Claude Code 自动压缩用哪个数文档没写，但更新日志里修过「最后一条回复报告用量为 0 时，自动压缩没触发」，说明它用到了回复里报告的用量。

## 单条结果太大怎么办

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 命令输出 | 成功：约 3 万字符内原样给，超出存文件，给路径和开头 2,000 字符；失败：约 1 万字符内原样给，超出只留首尾 | 先进 1 MiB 缓冲，超出留首尾；每次调用默认最多返回 1 万 token | 每个输出流在内存里留结尾 64,000 字节，全文写文件，告诉模型路径 |
| 读文件 | Read 一次 2.5 万 token，超出返回第一页和接着读的办法；整个文件超过 256 KB 拒绝 | 没有专门的读文件工具，用命令读，受命令输出的限制 | `read` 默认 2,000 行、每行 2,000 字符、一次 50 KiB |
| 所有工具共用的一层 | 没有，各工具各管各的；MCP 工具结果超过 2.5 万 token 存文件 | 写进历史时统一截掉中间，默认每条 1 万 token | 外溢插件：超过 12,500 token 留首尾，全文存文件，告诉模型怎么读；`read` 的结果不经过这层 |
| 截掉的部分模型能不能取回 | 成功的 Bash 和 MCP 大结果能，给了路径；失败的 Bash 不能 | 不能，全文只在记录文件里 | 能，给了路径，还说明用 `read` 分段读或者用 `grep` 搜 |

**一样：都在进历史之前处理，不调模型。** 三家都只按长度处理，codex 和 dsh 共用的那一层都是留首尾、删中间，并写明删了多少。

**不一样：截断有没有损失。** 这是三家在这一层最大的差别。dsh 把截断做成可恢复的：全文存在模型读得到的地方，并告诉模型怎么读。Claude Code 只对成功的大结果这样做，失败的大结果只截首尾、不留文件，文档没说为什么这样区分。codex 的截断是有损的：模型只知道删了多少 token，要看被删的部分，只能换个方式重新跑一次命令，比如加上 `grep` 或 `head`；命令有副作用或者跑得很慢时，这条路走不通。

**图片另算。** Claude Code 在图片累积到 API 的数量限制或自己的总大小限制时，成批删掉最旧的，一次删一批，缓存只重算一轮。dsh 在模型以「图片超出预算」拒绝请求时，把最旧的图片换成文字说明，写明是哪个附件、可读的路径在哪；这个决定记进日志，之后换模型、重放都沿用。codex 这一项本篇没核到对应的处理。

## 满了怎么压

<figure class="diagram">
<!--@include: ./figures/context-after-compact.svg-->
<figcaption>同一段对话压缩之后，三家各留下什么（示意，不按比例）。Claude Code 的文档只列了压缩后有哪些内容，没写先后，这一行的顺序是示意。codex 画的是本地摘要；服务端压缩的「压缩结果」是一段加密内容，保留的消息里还可能有钩子注入的提示。dsh 末尾原样保留的量默认是「窗口 − 输出预留」的 16%。</figcaption>
</figure>

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 触发 | 自动、手动、请求被拒后补救 | 回合开始前、回合中途、换模型前、手动 | 用量超过阈值、请求被拒后补救、手动、程序指定范围 |
| 摘要之前先做什么 | 文档说先清旧的工具输出，具体规则没公开 | 没有这一步；服务端压缩前只在历史超过窗口时截工具输出，让请求发得出去 | 剪枝：超过 8,192 字符的工具结果剪成首尾；剪完够了就不摘要 |
| 谁来压 | 会话用的模型；失败时换备用模型重试 | 用 OpenAI、Azure、Amazon Bedrock 时由服务端压缩；其他服务商由模型写摘要 | 默认是对话用的模型，可以另指定 |
| 压缩请求 | 系统提示词、工具、历史都不变，末尾追加压缩指令 | 服务端：和正常请求一样，末尾加一个触发项。本地：同样的系统指令和历史，末尾追加摘要提示词，不带工具定义 | 系统提示词、被选中的那一段、当前的工具，末尾追加压缩指令 |
| 摘要提示词 | 不公开；`/compact` 的说明和 CLAUDE.md 能影响 | 服务端的看不到；本地的 9 行，要求写四样 | 公开，固定八节，空的小节写 `(none)`；对话里已有上一次的摘要时要合并，不许照抄 |
| 原样留下什么 | 最近的往来 | 只有用户消息：服务端 6.4 万 token、本地 2 万 token 以内 | 末尾那一段，各种消息都有 |
| 压完装回来什么 | 项目 CLAUDE.md、记忆、git 状态、计划、读过或改过的文件（最多 5 个）、用过的技能 | 世界状态按新窗口完整渲染一遍 | 被遮掉的 `PromptContext` 快照 |
| 结果怎么记 | 一条边界记录加一条摘要消息 | 一条 `Compacted` 记录，窗口编号加一 | 一条遮住那一段的 `user/message`，外加 start、summary、end 三个事件 |
| 子代理 | 同样自动压缩，可以单独设压缩窗口 | 每个线程有自己的历史，各压各的 | 子会话有自己的日志，各压各的 |

**一样：压缩请求接在对话后面。** 三家都没有另起一个「请总结以下内容」的请求，而是在原来的历史后面追加一条压缩指令。Claude Code 的文档和 dsh 的源码注释给了同一个理由：这样摘要请求就是上一次请求的前缀加一条消息，能命中缓存；另起一个请求，整段对话都要重新计算，而且对话越长、越需要压缩的时候越贵。codex 的服务端压缩请求和正常请求结构一样；本地摘要不带工具定义，和正常请求的开头不完全相同，会不会因此用不上缓存，本篇没核。

**不一样一：压缩的单位。** Claude Code 和 dsh 压「较早的一段」，最近的原文留着，模型还能看到自己刚做过什么。codex 压「整个窗口」：新窗口里只有用户说过的话，模型自己的回复和工具输出一条不留，接下来怎么做全靠压缩结果。codex 本地摘要的写法也对应这一点：提示词要求写一份交给「接手的另一个模型」的交接摘要，放回历史时的前缀也告诉模型「另一个模型已经开始做了」。

**不一样二：压之前能不能省掉一次模型调用。** dsh 先剪大的工具结果，剪完够了就不摘要；Claude Code 的文档也说先清旧的工具输出，需要时再摘要。codex 没有这一层，到了阈值就压。

**不一样三：摘要看不看得到。** dsh 的模板公开，每次的摘要原文记在 `compaction/summary` 事件里。Claude Code 的提示词不公开，但 PostCompact 钩子能拿到摘要全文。codex 默认的服务端压缩返回加密内容，客户端看不到写了什么，也换不了提示词。

**摘要模板的松紧。** codex 本地的提示词 9 行，只列了要写的四样东西。dsh 规定八个小节，一节都不许省；它还专门处理了多次压缩：对话里已经有上一次的摘要时，保留仍然成立的、丢掉过期的、把新信息合并进同一套结构。Claude Code 的模板看不到，没法比较。

细节：[Claude Code](/agents/claude-code/context#满了怎么压) · [codex](/agents/codex/context#满了怎么压) · [dsh](/agents/deepseek-harness/context#满了怎么压)

## 压坏了怎么办

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 压完又立刻满 | 连续几次后停止自动压缩，报 thrashing 错误，交给人处理 | 源码注释写明不设防 | 每次补救重试前必须有可测量的进展，否则抛出原来的错误 |
| 正常请求因太长被拒 | 当场补救压缩，再发 | 把用量记成已满，这一轮报错结束；下一轮开始前先压缩 | 当场补救压缩后重试，默认最多 1 次 |
| 压缩本身失败 | 换备用模型重试；报错里写明失败原因 | 网络错误按退避重试；本地摘要超长时从最前面删一条再试；可以换当前模型再试一次 | 失败分成固定的六种，失败的尝试也记进日志 |
| 崩在压缩中间 | 文档没写 | 压缩完成后才写 `Compacted` 记录，崩在这之前，记录里就没有这次压缩 | start、summary、end 三个事件括起来，没有配对 end 的 start 能被发现 |
| 钩子拦下压缩 | 提前触发的，跳过这次压缩；被拒后补救的，直接报错 | 返回 `continue: false`，停下这一轮 | 没有钩子 |

**分歧最大的一处：压缩一直不见效怎么办。** 设想一个工具输出大到压完立刻又满：自动压缩一遍遍触发，每一遍都在调模型。三家给了三种答案，各有代价：

- **Claude Code 数次数**：实现简单，花费有上限；代价是可能在本来还能压下去的时候过早放弃。具体几次，文档没写。
- **codex 不设防**：源码注释的说法是，只要压缩能把用量压到远低于上限，就不用担心死循环。代价是压缩腾不出空间时，没有东西拦住它。
- **dsh 看进展**：只有 surface 真的被替换过（替换代数前进了），才允许重试。剪枝插件这边也有配套保证：每次剪出的结果都严格比输入小，同一条结果剪第二遍不会再有变化。代价是实现里必须有一个能测量的「进展」。

**被拒之后：当场补救，还是等下一轮。** Claude Code 和 dsh 当场压缩再重试，这一轮不中断。codex 让这一轮以错误结束，下一轮开始前的检查看到用量已满，再去压缩（据源码推断）。

**崩溃：只有 dsh 写成了明确的约定。** dsh 用一对加锁、解锁事件把压缩括起来，崩在中间留下的是一个能被发现的「没做完」，而不是一条声称已经完成的记录。codex 等压缩完成后才写 `Compacted` 记录，记录里带着替换后的整段历史；崩在这之前，恢复时就按压缩前的记录重建（据源码推断），但它没有「正在压缩」这样的标记。Claude Code 文档没写。

细节：[Claude Code](/agents/claude-code/context#压坏了怎么办) · [codex](/agents/codex/context#压坏了怎么办) · [dsh](/agents/deepseek-harness/context#压坏了怎么办)

## 模型能不能自己管

| | Claude Code | codex | dsh |
| --- | --- | --- | --- |
| 压缩或重开上下文的工具 | 没有 | 默认没有；实验开关 `token_budget` 下有 `new_context`（开新窗口，不摘要）和 `get_context_remaining`（查剩余 token） | 没有 |
| 回查被压掉的内容 | 没有 | 没有 | 实验包 `tool-session-query` 提供，默认没装 |
| 取回被截掉的输出 | 读 Bash、MCP 存下的文件 | 不能，只能重新跑命令 | 读外溢文件，提示里给了路径和读法 |
| 少占上下文的办法 | 派子代理；Read 分段读；用 ToolSearch 按需取工具定义 | 派子代理；调命令时用 `max_output_tokens` 限制输出；用 `tool_search` 按需取 MCP 工具 | 派子代理（`subagent`、`subagent_fork`）；`read` 分段读 |

**默认一样：模型管不了。** 三家默认都没给模型压缩或重开上下文的工具，压缩完全由 harness 和人决定。Claude Code 有一处可以对照：计划模式做成了模型能自己调用的工具，压缩却没有，文档没解释原因。

**实验方向不一样。** codex 和 dsh 都在试着给模型一个把手，方向相反。codex 的 `new_context` 让模型主动「扔掉重开」：不做摘要，直接开新窗口，文件、进程这些环境不动。dsh 的会话查询工具让模型「回头查」：被压掉的内容没有丢，变成能按序号读、能搜索的记录。两者现在都不是默认做法：codex 的开关还在开发中、默认关闭，dsh 的包要手动开启。
