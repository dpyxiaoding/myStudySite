# 上下文管理三家对读

<Badge type="info" text="agent-platform · 证据 · 2026-08-25" />

模型一次能记住的东西是有上限的，而编程智能体读一个文件就能把它撑满。Claude Code、codex、deepseek-harness 各自给了一整套答案——从装配、计量、裁剪、压缩到隔离，这份文档把三套答案拆成九个维度并排放。

- **3** 家并排：闭源 / Rust / TypeScript
- **9** 个维度，按上下文的生死排序
- **43**：codex 穷举出的上下文片段类型
- **80 / 90%**：dsh 与 codex 的自动压缩水位

## 先说清楚，这件事在解决什么

如果你没接触过智能体的内部，这一节是入口。已经熟悉的可以直接跳到下一节。

第一件反直觉的事：**模型没有记忆**。它不像人一样「记得刚才聊过什么」。每次你跟它说一句话，整段对话——从第一句开始——都要重新完整地念给它听一遍。你感觉到的「它记得」，其实是每一轮都把全文又发了一次。

第二件：它一次能听进去的量是固定的，这个量叫**上下文窗口**。单位是 `token`，大致相当于「词的碎片」——一个英文单词约 1.3 个 token，一个汉字约一个多。窗口写满了，下一句话就发不出去，会话直接卡死。

把这两件事放一起，约束就很硬了：对话只会变长不会自己变短；窗口大小是模型定的，你改不了；撞到上限不是「变慢」，是「报错，走不下去」。

第三件，也是编程智能体特有的：**工具输出把这个问题放大了不止一个量级**。让它读一个三千行的文件，那三千行要全文进窗口；让它跑一次测试，几千行日志也要进窗口。人跟人聊天一轮几十个 token，智能体一轮可能几万。**窗口不是被聊天撑满的，是被工具输出撑满的。**

## ① 模型看到的历史，到底「是」什么

你可能以为「对话历史」就是一个数组，往后 push 就行。**三家没有一家是这么做的**，原因很实际：压缩要求你能在历史里*认出*某一段是什么，并且把它替换掉。纯字符串拼接做不到——写进去之后，就分不出哪一段是「环境信息」、哪一段是「用户说的话」了。

::: claude 档 A · SDK 源码
会话落成 JSONL 文件，每条带 `uuid` 与 `parentUuid` 串成一条链。压缩在链上留下两样东西：一条 `compact_boundary` 条目（带 `logicalParentUuid` 反向指针，指向被压掉的那一段），和一条 `isCompactSummary` 消息。

关键在重建的时候：**刻意不跟随** `logicalParentUuid`。源码注释写明了理由——压缩之后，摘要那条消息已经代表了那一段内容，跟随反向指针会让内容重复出现。指针留着是给别的用途（人要回看历史）。

来源：`_internal/sessions.py:938`
:::

::: codex 全量源码
历史是 `ResponseItem` 序列，但注入进去的东西不是裸字符串，是**类型化片段**。每个片段实现 `ContextualUserFragment`，必须给出四样：

- `role()` —— 这段进 user 还是 developer
- `content_kind()` —— 一个稳定的 `<feature>.<name>` 分类
- `markers()` —— 起止标记
- `body()` —— 正文

`render()` 把标记和正文拼起来，`matches_text()` 反过来认出「这一段是不是我这一类」。`core/src/context/` 下有 **43 个片段类型**——能注入进上下文的每一种东西，都被穷举成了一个文件。

标记这一步是全部机制的地基：它让历史里的注入内容**可被机器识别**，于是可以在下一轮被替换、被跳过、被差分。
:::

::: dsh 全量源码 + 自带文档
日志只增不改，模型看到的是日志上的一层投影，叫 **surface**。只有三种事件能进 surface：`user/message`、`assistant/message`、`tool/result`。每一条都必须声明自己怎么进：

- `'append'` —— 追加到尾部，正常路径
- `{op:'replace', start, end}` —— 用这一条**遮蔽**掉 `start` 到 `end` 之间的节点

压缩就是靠 replace 实现的：摘要作为一条新的 `user/message` 追加进日志，同时声明遮蔽掉被摘要的那一段。**日志里那一段原样还在**（人读的完整记录读的是原始事件），只是不再进模型。

一个副作用值得记：序号可以非单调——一次 replace 会把一个高序号的摘要节点放到旧位置上，所以「被遮蔽的序号集合」才是权威，位置对只是辅助。
:::

::: tip 同一个问题，三种不同的「后悔药」。
dsh 的原始内容永远还在（日志只增不改）；Claude Code 的原始内容也还在（记录文件里），但重建时主动跳过；codex 的片段被裁掉之后，靠标记在下一轮自动补回。这一维决定了后面所有维度的上限——你能不能撤销一次压缩，在这里就定死了。
:::

## ② 装配的分层：为什么顺序比内容还重要

每次请求都要把系统提示词、工具定义、项目规则、整段对话重新发一遍。全部重算太贵，所以厂商提供**提示词缓存**：如果这次请求的开头和上次一模一样，那一段就不用重算，便宜十倍以上。

但缓存是**前缀精确匹配**——从第一个 token 开始比，撞到第一处不一样就停，**后面全部重算**。这一条规则单独决定了三家的装配结构，而且逼出了同一个答案：变得慢的放前面，变得快的放后面，会话中途要注入的东西一律追加到末尾，绝不回头改前面。

::: claude 档 B · 官方文档
按「多久变一次」排成三层：

| 层 | 装什么 | 什么时候变 |
| --- | --- | --- |
| 系统提示词 | 核心指令、工具定义、输出风格 | 工具集合变了，或版本升级 |
| 项目上下文 | CLAUDE.md、自动记忆、无作用域规则 | 会话开始，或 `/clear`、`/compact` 之后 |
| 对话 | 消息、回复、工具结果 | 每一轮 |

不在提示词文本里、但同样进缓存键的两样：**模型**和 **effort 档**。换任意一个，整条历史重算。缓存有效期：订阅档 1 小时，API key 与第三方 provider 5 分钟。

一个反直觉的推论：`/rewind` 把对话截断回更早一轮**不会**让缓存失效——那个前缀本来就在缓存里。所以**回退比压缩便宜**：压缩要造一个新前缀，回退是回到一个旧的。
:::

::: codex 全量源码
做法是**世界状态快照加差分**。`core/src/context/world_state/` 下有 16 个真实的 section（另有一个测试支撑文件）：模型、权限、人格、环境、AGENTS.md、协作模式、工具、上下文窗口指引……每个实现两个方法：`snapshot()` 给出一份 JSON，`render_diff(previous)` 只在真的变了的时候产出一个片段。

差分还要处理一个麻烦：**上一次注入的那一条，还在历史里吗？** 它会扫历史找匹配的片段，找不到就当「缺席」（重新全量注入），找到旧格式就当「未知」。于是压缩把旧片段裁掉之后，下一步会**自动补回来**——靠的正是维度 ① 那套标记。
:::

::: dsh 全量源码 + 自带文档
只有两个注册类型，而它们的差别就是这件事：

- `PromptSection` 进系统提示词，按 `order` 升序拼（约定 `-100` 是 harness 身份、`0` 是部署人格、`100–199` 是工具指引）。基本不变。
- `PromptContext` 是**保留历史之后的一条 user 角色快照**，文档原话是「`PromptSection` 的缓存安全对应物」。变了就追加一份新的完整快照。

最直白的例子在审批那一节：用户切换权限档，新状态以一条新消息追加，**不重写请求头里的系统提示词**——所以切权限不会废掉整条缓存。
:::

::: tip 这是全文最有分量的一处一致。
三个团队、三种语言、三套架构，在「中途注入的东西一律追加成对话消息、不动前缀」这一条上给出了逐字相同的答案。三个独立实现走到同一处，基本可以当定论用——本仓 §5.9 写的「skill 正文注入 `messages` 末尾，不进 `system`」正是它。
:::

## ③ 计量：怎么知道已经用了多少

听起来这不该是个问题——API 返回里不是有用量吗？有三个坑：

1. 用量是**上一次请求**的结果，而你要决定的是**这一次**发不发得出去
2. 你本地刚拼进去的东西（这一轮的工具输出）还没有任何用量数据
3. 换个模型、换套工具，同样的历史算出来的 token 数就变了

::: claude 档 A · SDK 源码
三家里唯一把「谁在吃我的上下文」做成用户能直接看的一张账单。`/context` 命令按类别拆账，SDK 里的 `ContextUsageResponse` 把这张账单完整暴露出来：

- `categories` —— 每一类多少 token
- 明细字段一长串：`systemPromptSections`、`systemTools`、`mcpTools`、`memoryFiles`、`agents`、`skills`、`slashCommands`、`deferredBuiltinTools`
- `rawMaxTokens` 是模型的真实窗口；`maxTokens` 是**有效上限**——注释原话是「可能被自动压缩的缓冲区调低」，也就是自动压缩会预留一块地方，把有效上限压到真实窗口之下
- `autoCompactThreshold` —— 触发自动压缩的 token 阈值

来源：`types.py:764–830`
:::

::: codex 全量源码
`ContextWindowTokenStatus` 有八个字段，关键是它支持**两种口径**：

- `Total` —— 按整个活跃上下文算
- `BodyAfterPrefix` —— **只算初始前缀之后新增的**。它把会话开头那一大坨（系统提示词、工具定义、AGENTS.md）从预算里扣掉，只盯着「这轮对话自己长出来的部分」

配套的 `AutoCompactWindow` 让上下文窗口变成一个有身份的对象：首个 / 上一个 / 当前三个 UUID 串成链，还记着预填 token 数（区分服务端实测与本地估算）、「预算提醒投递过没有」、「模型请求过换新窗口没有」。

默认阈值是窗口的 **90%**：`auto_compact_token_limit()` = min(配置值, 窗口 × 9/10)。

来源：`protocol/src/openai_models.rs:486` · `session/context_window.rs`
:::

::: dsh 全量源码 + 自带文档
`TokenMeter` 是三家里最讲究的一个：它把「什么时候可以相信厂商给的数字」做成了一条严格前提。

`measure()` 返回一个快照，含锚点、`totalTokens`（请求加响应的压力）、`surfaceTokens`（surface 的启发式总量）、带符号的 `surfaceDeltaTokens`、以及 `nodes`——**每个 surface 节点各自多少 token**。

复用厂商真实用量只在两个条件同时成立时才允许：最近一次成功调用的**规范请求信封完全一致**，且它的总数不低于那次调用的完整启发式锚点。否则退回估算档，整包按固定启发式重新定价。

带符号的差值是为了同时表达增长和缩减（压缩之后 surface 是变小的）。每次测量绑一个「已消费的持久事件数」，所以测量是可重放的。

默认阈值是窗口的 **80%**。

来源：`compaction-basic/src/config.ts:20` · `llm/token-meter/src/types.ts`
:::

## ④ 压缩之前的那一层：即时裁剪与外溢

这一层最容易被漏掉，但它才是编程智能体的主战场。等到窗口 80% 满了再压缩已经晚了——**一条命令读一个 5MB 的日志，就能一次性把窗口打满**。所以三家都在工具结果*进入历史之前*先砍一刀。

要跟压缩分清楚：裁剪是**当场的、没有模型参与的、按字节或 token 的机械操作**；压缩是事后的、要调一次模型的、按语义的。

::: claude 档 B · 官方文档
bash 工具的回读窗口默认 **30,000 字符**，上限 150,000。超出时给文件路径加一段预览，让模型自己决定要不要再去读。工作文件另有 5GB 上限。

它还把「**工具定义本身占地方**」当成同一类问题：50 个工具的定义要占 10–20K token，而超过 30–50 个工具之后，模型选工具的准确率开始下降。于是有了 tool search——启用判据是「可延迟的工具定义 token 占上下文窗口的 10%」，目录最多 10,000 个工具，每次搜索返回最多 5 个。**工具定义按需加载**，不再一次性全塞进系统提示词。
:::

::: codex 全量源码
`truncate_middle_with_token_budget(s, max_tokens)`——**按 token 预算做中间截断**，不是按字节。头尾保留，中间挖掉。内部常量 `APPROX_BYTES_PER_TOKEN = 4`。

用在哪：沙箱错误信息给 900 token 的预算，工具拒绝消息有自己的上限。

安全审查那条链截断时会留一个可解析的标记：`<truncated omitted_approx_tokens="N" />`——**省掉了多少也一并告诉模型**。

来源：`utils/string/src/truncate.rs` · `guardian/prompt.rs:651`
:::

::: dsh 全量源码 + 自带文档
三家里唯一把这一层做成独立架构的，拆成三段：

**保留库**（`output-retention`）：两种保留器，按资源模型分而不是按参数分。`ItemRetainer` 管有序的逻辑单位（文件路径、grep 命中、搜索来源），第一版只支持保留头部；`TextRetainer` 管字节流（bash 输出、网页正文），支持头 / 尾 / 头尾三种，并在收尾时保住 UTF-8 边界。

它还钉死了一个语义边界，头注释原话：`truncated` 表示「保留器因为预算省略了*本来拿得到*的内容」，**不是**「上游本身就不完整」。权限失败、跳过的二进制文件、provider 部分失败一律留在工具自己的字段里，绝不折进 `truncated`。这个区分很多实现都糊在一起。

**存储接缝**（`spill`）：超过 `maxInlineBytes` 的纯文本结果，把**全文**存盘，返回一个不透明的定位符、精确字节数、和一句检索提示。本地后端写在 `<root>/session-<sha256>/<random>-<safeName>`，根目录 0700，写入用 `open(path,'wx',0o600)` 独占——防的是别人预先放一个符号链接把写入重定向出去。

**策略消费者**（`spill-policy`）：用「头尾预览 + 存盘引用」替换掉超标的内联结果，而且是尽力而为——存盘失败就保留原来的内联结果，**不把一次成功的调用变成错误**。细节：那句提示自己的字节成本要算进 `maxInlineBytes` 之内。

这一层在模型那边是看得见的。`grep` 工具的描述里就写着：前 250 条内联，超出则报告完整列表存到了哪里。
:::

::: tip Claude Code 与 codex 是「截断，并告诉你截了多少」；dsh 是「截断，全文留在一个可检索的地方，并告诉模型怎么去取」。
后者把裁剪从*有损*变成了*可逆*——这条线一直连到维度 ⑧，在那里它会长成一整组模型可调的检索工具。
:::

## ⑤ 压缩本身：什么时候压、在哪一步压、怎么压

压缩就是「让模型把前面一大段总结成一小段，用总结替换原文」。听起来简单，实际是四个彼此独立的决策，三家在每一个上都分了岔。

### 决策一 · 什么时候压

::: claude
阈值到了就压；也可以人工 `/compact`，还能带焦点：`/compact focus on the API changes`。CLAUDE.md 里可以写一段 Compact Instructions 长期生效。
:::

::: codex
把「为什么压」做成了一个分类空间，六个枚举维度全部打点进分析：

| 维度 | 取值 |
| --- | --- |
| Trigger | Manual / Auto |
| Reason | UserRequested / ContextLimit / **ModelDownshift** / **CompHashChanged** |
| Implementation | Responses / **ResponsesCompactionV2** / ResponsesCompact |
| Phase | StandaloneTurn / PreTurn / **MidTurn** |
| Strategy | Memento / PrefixCompaction |
| Status | Completed / Failed / Interrupted |

两个取值值得注意：`ModelDownshift`（换到一个窗口更小的模型，所以要压）、`CompHashChanged`（压缩逻辑本身的哈希变了）。

来源：`analytics/src/facts.rs:399` 起
:::

::: dsh
两个自动触发因由：`pressure`（压力到阈值），`context-overflow`（**provider 明确回了窗口超限**，也就是已经撞墙之后的补救）。

外加一个 `compactNow()`：会话空闲时做一次「即使没到阈值也值得做的」缩减，没有有用的范围就返回空、什么都不写。
:::

### 决策二 · 在哪一步压

这是最容易出错的一处。dsh 固定在 `agent/pre-step`、请求推导之前，串行执行。codex 分三处，而且**回合中途压缩必须特殊处理**——`compact.rs` 里的 `InitialContextInjection` 枚举把规则写死了：回合前压缩和手动压缩用 `DoNotInject`（清掉引用，下一轮全量重注）；回合中压缩必须用 `BeforeLastUserMessage`。

::: tip 这条理由值得单独记。
codex 给出的原因是：**模型被训练成把压缩摘要看作历史的最后一项**，所以初始上下文必须插在最后一条真实用户消息*之上*。也就是说，压缩产物的形状不是可以自由设计的，它被模型的训练分布锁住了——这类约束在文档里搜不到，只有读到那一行注释才知道。
:::

### 决策三 · 怎么压

::: claude
两级，顺序写死。文档原话：「先清掉较早的工具输出，需要的话再对对话做摘要。」
:::

::: codex
三种实现并存，其中两种是另外两家完全没有的档次：

- **服务端压缩**（`compact_remote*.rs` 约 2,000 行）——摘要这件事由 OpenAI 的 Responses API 侧完成，本地只负责发起与记账。
- **换窗口但不摘要**（`compact_token_budget.rs`）。

> 跳过模型/服务端摘要，改为装一个全新的上下文窗口。它仍然被建模成一次压缩，好让 compact hook 与 `ContextCompaction` 观察到同样的生命周期。
>
> —— `core/src/compact_token_budget.rs` 头注释

换句话说：换了新白板，但对外还是报告「压缩完成了」，因为下游全是按那个形状写的。
:::

::: dsh
剪枝先跑，在范围选择之前，把超预算的 `tool/result` 改写成「头 + 固定省略标记 + 尾」，然后重新测量——**如果这一步就够了，就不摘要了**。

默认预算：`thresholdChars` 8192、`headChars` 4096、`tailChars` 1024。原事件仍然完整留在日志里。

保留策略：`retainRatio` 默认 0.16，窗口末尾 16% 的内容不参与压缩。
:::

### 决策四 · 摘要要写成什么样

三家的摘要提示词能直接对读，风格差异比想象中大。

::: codex 9 行，松散
`prompts/templates/compact/prompt.md` 整篇 9 行，要求四样：当前进展与关键决策、重要上下文与约束、还剩什么没做、继续所需的关键数据。收尾一句 “Be concise, structured”。

另有一个 `summary_prefix.md`，一句话把摘要框给下一个模型：

> 另一个语言模型开始解决这个问题，并产出了一份它思考过程的摘要。你同时能看到那个模型用过的工具的状态。用这些信息在已完成的工作上继续，避免重复劳动。
>
> —— `prompts/templates/compact/summary_prefix.md`
:::

::: dsh 八节硬结构
模板是八个小节，**一节都不许丢**：

```md{1,7}
## Primary Request and Intent   ← 用户目标，措辞重要处逐字引用
## Key Technical Concepts       技术、框架、模式、约定
## Files and Code               精确路径 + 为什么重要
## Errors and Fixes             错误怎么解决的 + 用户反馈
## Pending Jobs                 要求过但没做完的
## Current Work                 此刻正在做什么
## Next Step                    ← 单独一个下一步，或 (none)
## Critical Context             决策与理由、约束、待决问题
```

空的小节必须写 `(none)`，规则原文 “never drop a section”。还有一条：如果对话里已经有一个 `<compacted-summary>` 块，那是**上一次的检查点**，不许照抄——要保留仍然成立的事实、丢掉过期的、把新信息合并进同一套结构。
:::

::: claude 不可见
模板本身读不到（引擎闭源），只知道它能被 CLAUDE.md 里的 Compact Instructions 与 `/compact focus on X` 影响。这一格是本文档的一处空白，不是一个结论。
:::

::: tip dsh 有一处非常漂亮的工程细节：压缩这个动作本身，也被缓存优化了。
摘要指令是作为回放对话之后的*最后一条 user 消息*投递的，而不是另起一个「摘要器的 system prompt」。头注释写明了理由——保持会话自己的系统提示词、工具和消息前缀在它前面，这次辅助调用就成了上一次路由请求的**真前缀**，于是 provider 的缓存能被复用，而不是失效。这正是维度 ② 那条规则被贯彻到底的样子。
:::

## ⑥ 不变量与失败语义：崩在中间会怎样

压缩是一个多步操作——调模型、拿摘要、改历史、落盘。中间任何一步崩掉，会话会变成什么样？这一维几乎全部证据来自 dsh，因为只有它把这件事写成了显式的契约。

### 工具调用与结果必须配对

dsh 为此导出两个检查函数，分别验证压缩前后的配对平衡。范围可以**拆开一个回合**（一个超大回合的早期步骤可以先压掉），但**不能拆开一对调用与结果**——留一个没有结果的调用在历史里，模型会困惑，有些 provider 直接报错。

### 锁最后释放

dsh 用三个只进日志的事件把压缩括起来：`compaction/start` → `compaction/summary` → `compaction/end`。锁括住**整个**操作：先写 start，然后摘要、摘要记录、承载摘要的那条消息替换*全部*落地，最后才写 end。

::: tip 崩在中间留下的是一个可检测的孤儿锁，而不是一条谎称压缩完成了的结束事件。
前者能被发现并修复，后者会让后续所有推理建立在一个假事实上。这与本仓「记账排在终态之前」是同一条推理。
:::

### 记到足以重建

`compaction/summary` 的载荷包括摘要、原始输出、被遮蔽的范围与序号集合、token 数、provider、model、生成上限、用量——目标写在文档里：从「日志 + 代码」能重建那次一次性请求。

### 失败分类是封闭集合

dsh 只有六种失败：`busy` / `cancelled` / `changed` / `summary` / `commit` / `persistence`。其中 `changed` 与 `summary` 不改变会话 surface，但**仍然把失败的尝试关闭并持久化进日志**——失败也是事实。codex 那一侧对应的是完成 / 失败 / 中断三态。

### 崩溃恢复不截断

dsh 重载到一个「有回合开始、没有回合结束」的日志时，补一条合成的结束事件，理由标为 `interrupted`。这个理由是**唯一一个没有任何正常循环会发出的**，所以它一出现就表示「这是恢复补的」。背后的判断是：长程任务里一个回合可能极大，那些事件在崩溃前已经落盘了，截断等于扔掉真实完成的工作。

### 图像有单独预算

codex 有一整个 `compact_remote_v2_images.rs` 加一份图像预算测试——图片按 token 计价的方式和文本不同，压缩时要单独管。另外两家在源码层面没有看到对应物；**但 Claude Code 引擎闭源，这不构成「它没有」的结论。**

## ⑦ 死循环保护：三家给了三个不同答案

这是全文最尖锐的一处分歧，而且它的失效方式是烧钱。

设想有一个工具输出大到「摘要完了立刻又满」。自动压缩触发 → 压完还是超 → 再触发 → 无限循环，**每一轮都在调模型**。这道闸怎么设计？

::: claude 计数停机
文档写明：几次尝试之后，**停止自动压缩并报错**，把决定权交回给人。
:::

::: codex 明确选择不做
> as long as compaction works well in getting us way below the token limit, we shouldn't worry about being in an infinite loop.
>
> —— `core/src/session/turn.rs`

也就是它**意识到了**这个风险，赌的是「压缩总能腾够空间」。这是一个被写下来的取舍，不是疏漏。
:::

::: dsh 要求单调量推进
失败请求的恢复，只有在 **surface 替换代数真的推进了**的前提下才开一个新的重试回合；否则原来的请求错误仍然权威。

配套的保证在剪枝器那一侧：每次产出的替换结果**严格小于触发它的输入**，所以第二遍必然不再产出替换。单调性是被实现*保证*的，不是被计数*近似*的。
:::

::: tip 三种代价，本仓要自己挑一种。
计数停机会在本来还能压下去的场合过早放弃；不设闸的失效方式是死循环烧钱；单调量最严谨，但要求你在实现里真的有一个能推进的量可以盯。**本仓 §9.10 这道闸目前是空的**，而触发条件我们完全具备——bash 的输出没有上限约束，读一个大文件就能撑满。
:::

## ⑧ 让模型自己参与：两条完全不同的路

到这里为止，上下文管理都是 harness 背着模型做的。但模型自己是知道「我快想不起来前面的事了」的。要不要给它一个把手？

::: codex 给的把手是「扔掉」
它有一个真正的工具，模型可以自己调。名字 `new_context`，无参数，描述一句话：

> Start a new context window. Does not clear, reset, or otherwise affect environment state.
>
> 调用之后返回：A new context window will start without summarizing conversation history.
>
> —— `tools/handlers/new_context_window_spec.rs`

**不摘要，直接换一块新白板**，但环境状态（文件、进程）一点不动。

配套的还有讲给模型听的东西：`ContextWindowGuidance` 是一个 developer 角色的片段，用专门的开闭标签包着，告诉模型当前窗口的状况；`TokenBudgetContext` 的分类就叫 `token_budget.context_window`。而且提醒只投一次——窗口对象里有个布尔记着投过没有。
:::

::: dsh 给的把手是「捞回来」
它没有「换窗口」这种工具，但有一组会话查询工具，**模型能回查自己的日志**：

- `session_event_read` —— 按序号读一条完整未删节的事件，还能带前后各若干条的摘要
- `session_event_search` —— 在本会话的历史事件里搜（当前会话会排除掉正在执行这次调用的那一步）
- `session_event_trace` / `session_trace` —— 追踪
- `session_search` —— **跨会话**搜，在调用者的工作区里搜之前的会话，每个会话返回最强匹配的那一条

这是维度 ① 那个设计的直接兑现：日志只增不改，所以**被压缩掉的东西并没有消失，它变成了一个可检索的数据库**。模型的上下文满了不要紧，它知道去哪里查。

配套的还有目标持久化：`create_goal` / `get_goal` / `update_goal` 把长程目标存在对话之外，压缩再怎么发生，目标本身不会被摘要掉。工具描述里明写「当直接的人类请求是一个应该跨自主轮次持续的长期目标时」创建，并且**拒绝非人类与子智能体的权限**。
:::

::: claude 把手给人，不给模型
模型侧没有可调的上下文工具。控制权全部留在人这边：`/compact focus on X` 由人指定焦点，CLAUDE.md 里的 Compact Instructions 由人长期配置，`/rewind` 由人选择回到哪一轮——菜单有六个动作：恢复代码加对话 / 只恢复对话 / 只恢复代码 / **从这里往后摘要** / **摘要到这里为止** / 取消。

自动追踪的检查点每条用户提示建一个，一个会话保留最近 100 个，随会话存盘，30 天清理。
:::

::: tip 这是三家世界观差异最直白的一处兑现。
codex 认为上下文是*可重置的窗口*，所以给模型一个重置按钮；dsh 认为上下文是*日志上的投影*，所以给模型一个查询接口；Claude Code 认为上下文是*一条要保护的缓存流水线*，所以把控制权留给人——避免模型自己把前缀弄脏。三个答案都自洽，因为三个前提本来就不同。
:::

## ⑨ 隔离：不让它进来，就不用管它

最后一条路根本不是「怎么腾地方」，而是「怎么让它一开始就不占地方」。**子智能体**就是这个答案：派一个独立的智能体去做一件事，它烧它自己的上下文，只把结论带回来。

三家在工具描述里都说得很直白。dsh 的子智能体工具是这么写的：

> 把一个自洽的任务委派给子智能体（一个在自己的上下文里工作的独立智能体），把聚焦的、独立的工作卸载出去——研究、限定范围的实现、一次分析——**这样它不消耗这段对话的上下文**。子智能体返回它的结果，不返回它的中间步骤。给它一个完整的、能独立成立的提示词：它看不到这段对话。
>
> —— `docs/tool-catalog.md` · subagent

隔离程度上，三家有细微但重要的差别：

::: claude 档 A
- 子智能体的记录是一条支线
- 源码注释写明：比主会话简单——**没有压缩、没有支线、没有保留段**
- 也就是子智能体不做压缩，生命周期短到不需要

来源：`sessions.py:1249`
:::

::: codex 全量源码
- 多智能体是一等公民，光片段类型就有一组
- 跨智能体消息、完成通知、模式指引、角色指引、用量提示各一个文件
- 「另一个智能体说了什么」是**有类型的注入**，不是普通消息

所以它同样能被差分、被替换、被识别。
:::

::: dsh 全量源码
- 分叉会话**继承**种子日志里已有的外溢定位符
- 那些产物**不被复制、不被改属主**
- 分叉之后新产生的外溢用子会话的 id

把维度 ④ 的外溢机制和会话分叉正确接上了。
:::

顺带：维度 ④ 提到的 tool search 其实也是隔离——把工具*定义*挡在上下文外面，用的时候再取。codex 的 Code Mode 是同一道题的另一个答案。「隔离」这条路比看起来宽。

## 对本仓意味着什么

按本仓规矩，证据文档**不作决定**。下面只做分类，每一条指向要读的那一节。

### 同构 —— 三家都这么做，可以当定论

- **中途注入追加成对话消息、不动系统提示词前缀。** 本仓 §5.9 写的「skill 正文注入 `messages` 末尾，不进 `system`」与三家逐字同构。三个独立实现走到同一答案，这是最强的一类佐证。
- **压缩「先裁剪后摘要」的顺序。** 与 Claude Code 的两级顺序、dsh 的剪枝先行一致。本仓 §9.10 已经写对了。

### 本仓没有 —— 补不补是决策，本文不作

- **死循环那道闸**（§9.10）。三个可选答案在维度 ⑦，代价各不相同。触发条件本仓完全具备——bash 的输出没有上限约束，读一个大文件就能撑满。
- **逐类别的上下文账单**（§9.4）。目前只有「读用量」这一层，没有「谁在吃我的上下文」。
- **工具结果的外溢与检索**（§5.10 与 §9.10 之间）。维度 ④ 那套「存全文 + 定位符 + 检索提示」本仓没有对应物。
- **压缩的失败语义与锁**（§6.2 / §9.10）。崩在压缩中间会留下什么，目前没有定义。

### 三家分歧 —— 要自己判，没有现成答案

- **模型要不要有上下文的把手**（维度 ⑧）。给了就要面对「模型自己把缓存前缀弄脏」的风险，不给就只能靠 harness 猜。
- **阈值按哪种口径算**（维度 ③）。本仓装配期有自动发现（skills、pack、profile），初始前缀会很大——这时 codex 的「只算前缀之后」口径值得认真考虑。
