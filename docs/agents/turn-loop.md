# 回合循环与中断

<Badge type="info" text="Evidence · 三家对读" /> <Badge type="info" text="agent-platform · 证据 · 2026-08-26" />

「工具调用的三条路」讲的是工具怎么进入模型的视野。这一份讲循环本身：**一个回合从哪里开始到哪里结束、什么让它继续、什么让它停，以及有人按下 Esc 的那一刻，代码里发生的事情按什么顺序发生**。九个维度，四处同构、五处分岔。

- **3** 种「一个回合」的定义，互不等价
- **5** 处三家互相矛盾
- **10** dsh 每步默认并行工具上限
- **552ms** 对标实测：插话从入队到注入

## 先说清楚，这件事在解决什么

「模型说要调工具，就去调，把结果给它，再问一次」——循环的骨架一句话说得完。难的全在这句话的缝隙里，而且这些缝隙都只有在有人使用的时候才显形。

**第一，回合不是一个自然单位，是一个被定义出来的单位**。用户敲一次回车算一轮？那模型连着调八次工具算几轮？自动压缩算不算一轮？这个定义决定了「最多跑几轮」这道闸拦在哪里，也决定了界面上那个进度条按什么走。三家给了三个不同的答案，而且它们不能互相翻译。

**第二，循环运行的时候，外面的人还在动**。他会补一句话，会按 Esc，会改主意。这些输入必须落在某个边界上——落错地方的后果不是崩溃，是模型收到一份自相矛盾的历史。

**第三，中断是有顺序的**。取消信号要传到几个地方：在飞的模型请求、在跑的工具、在等的审批。这几件事的先后不是实现细节——顺序错了，用户按 Esc 会在模型的历史里变成「用户拒绝了这次调用」。

**第四，「停下」有很多种，而它们在审计里必须长得不一样**。跑完了、用户叫停、预算耗尽、模型出错、卡在原地——把这些揉成一个 `failed`，事后就分不清哪次是系统的问题。

九个维度：① 回合的边界 → ② 靠什么继续、靠什么停 → ③ 工具的并发与回填 → ④ 跑动中插话 → ⑤ 中断的时序 → ⑥ 中断之后模型看到什么 → ⑦ 失败分类与重试 → ⑧ 上界：轮次、token、钱、时间 → ⑨ 原地打转

## ① 一个「回合」到底是什么

这不是术语问题。它决定了「最多几轮」这道闸拦在哪、进度条怎么走、以及压缩这件事算不算占用了用户的一轮。

::: claude 一问一答 | 档 B · 定义写在文档字符串里
- `max_turns` 的说明原话：**「一个 turn 由一条用户消息和一次助手回应组成」**
- 也就是中间调多少次工具都还是同一轮
- 结果消息里带 `num_turns`，是这个口径下的计数

来源：`types.py` · `ClaudeAgentOptions.max_turns`
:::

::: codex 三层，且压缩占一层 | 全量源码
- thread → turn → step。turn 是用户的一次提交，step 是**一次采样请求**
- `StepContext` 的定义写着「可能在采样请求之间变化的、请求作用域的状态」——里面装着模型信息、推理档、**审批策略与裁决人**
- 审批策略是 per-step 的，注释给了理由：模型切换时 Guardian 的要求可能变
- `TaskKind` 只有三个值：`Regular` / `Review` / `Compact`——**压缩和评审各占一个 turn 槽位**，一个会话同时只能有一个活动 turn

来源：`core/src/session/step_context.rs` · `core/src/state/turn.rs`
:::

::: dsh 两层加一个相位 | 全量源码
- turn / step 两层，另有一个驱动器相位：`idle` / `maintenance` / `running`
- `maintenance` 是给「不是用户回合、但也不是空闲」的活儿留的位置
- 对外只暴露两个状态：`AgentStatus = 'idle' | 'running'`。注释特意写明**销毁不是第三种可观测状态**

来源：`core/agent-loop/src/agent.ts` · `core/agent/src/runtime-types.ts`
:::

::: warning 分岔
三个定义不能互相翻译。Claude Code 的一轮里可能有 codex 的十个 step；codex 把压缩记成一个占槽位的 turn，另外两家不这么算。本仓是 Run → 轮 → 步三层，Checkpoint 落在步边界上，与 codex 最接近——但本仓的压缩是循环内的一轮，不占独立槽位。

实用的推论只有一条：**看到「最多 N 轮」这种配置项，先问它的 turn 是哪一个**。同一个数字在三家意味着完全不同的花费上界。
:::

## ② 靠什么继续，靠什么停

循环体跑完一遍，怎么判断要不要再来一遍？停下来的时候，怎么记它为什么停？

::: codex 一个布尔或 | 全量源码
- 主循环的续跑判据是一行：`needs_follow_up = model_needs_follow_up || has_pending_input`
- 也就是**两个来源**：模型还有活要干，或者队列里还有人说了话
- 停止原因是 `TurnAbortReason` 四值：`Interrupted` / `Replaced` / `ReviewEnded` / `BudgetLimited`
- `Replaced` 值得注意——**新回合顶掉旧回合也是一种中止**，它和用户按 Esc 在审计里不是一回事

来源：`core/src/session/turn.rs:400` · `protocol/src/protocol.rs`
:::

::: dsh 六值，每个都写了谁生产 | 全量源码
- `TurnEndReason`：`completed` / `aborted`（带原因）/ `blocked` / `error`（带结构化失败）/ `max-tokens` / `interrupted`
- `interrupted` 那一条的注释写着「**循环从不发出这个标记**」——它只由持久化后端在重载时关闭崩溃孤儿回合用
- 也就是说「被取消」与「崩掉了」在取值域里是两个值，且各自只有一个生产者
- 类型本身可合并扩展：插件往映射里加变体

来源：`core/session/src/types.ts` · `TurnEndReasonMap`
:::

::: claude 两个字段各管一半 | 档 B
- 结果消息里 `stop_reason` 与 `terminal_reason` 并存
- 后者的取值举例是 `completed` / `max_turns` / `aborted_streaming` / `aborted_tools`
- **中止分两格：断在流式输出里，还是断在工具执行里**
- 没报 terminal reason 的情况也写明了：老版本 CLI，或绕过循环的本地斜杠命令

来源：`types.py` · `ResultMessage.terminal_reason`
:::

::: tip 同构
三家都把「为什么停」做成**封闭取值域**，而不是一句自由文本。本仓也在这条线上：`TerminalOutcome` 三种终态，而且做了一处更细的区分——`cancelled` 不带 `RunFailureCode`，注释写明理由：**它不是一种失败，是用户改主意了；给它编一个失败码会让「用户主动停的」和「跑挂了」在审计里长成同一个形状。**

值得抄的一格是 codex 的 `Replaced`：本仓目前没有「新回合顶掉旧回合」这个概念，而 M2 有 server 之后，同一个 Session 上来两条请求是会发生的。
:::

## ③ 工具的并发与回填

模型一次给了五个工具调用。哪些能同时跑？结果按什么顺序交回去？

::: codex 一把读写锁当闸 | 全量源码
- 一把 `RwLock<()>`：支持并行的工具取**读锁**（彼此可以重叠），不支持的取**写锁**（独占，等所有在跑的排干）
- 注释指出通过这道闸的那一刻才是「派发等待结束、处理器执行开始」的分界，计时按这个分
- 另一句很细：**工具调用可能晚于它所属的 step 才跑，所以要保留「当初把这把工具广告出去的那个 step」的上下文**——执行时用的审批策略是它被广告时的那一份

来源：`core/src/tools/parallel.rs`
:::

::: dsh 有界滚动池 + 模型顺序 | 全量源码
- 独占调用形成 barrier；并行调用走一个**有界滚动池**，默认上限 10，且在启动前重新分类一次
- 头注释里那句是这一维的核心：**「派发可以重叠，而策略、结果与结果上下文保持模型顺序」**
- 中止时停止补充、把已启动的排干，并**为被跳过的调用记录合成错误结果**，理由写明是「好让重放保持有效」
- 但调度器自己出致命故障时，保留已记录的 `tool/call` 事件，**不伪造结果**

来源：`core/agent-loop/src/tool-calls.ts`
:::

::: ours 按连续段切 | 本仓源码
- 把连续的、可并行且**静态上界就是 `read`** 的调用并成一组，其余各自单独一组
- 按「连续段」而不是「把所有可并行的挑出来一起跑」，理由是模型给的调用顺序有语义
- 判据必须是静态的 `maxRisk`：分组要在 `prepare` 之前定，而实际风险要 `prepare` 完才知道

来源：`core-runtime/src/loop/tool-turn.ts`
:::

::: tip 同构一条，分岔一条
**同构的是「结果必须按模型给的顺序回填**」。dsh 把它写成一句话的不变量，codex 用锁保证，本仓靠分组保证。没有一家允许结果乱序交回去——那会让模型对不上自己的调用。

**分岔的是准入判据**。codex 问工具自己「你支不支持并行」，dsh 在启动前重新分类一次，本仓要求**静态风险上界就是只读**——三条里本仓最保守，而保守的理由（分组必须早于风险判定）是另外两家没有的约束，因为本仓的风险判定要读参数。

dsh 那对相反的处置值得单独记：**中止时伪造结果，调度器自己挂了时不伪造**。判据与本仓 ADR-0081「这一步派发过工具没有」同源——知道发生了什么就补齐，不知道就别编。
:::

## ④ 跑动中插话

模型正在跑，用户补一句「顺便把这个也改了」。这句话什么时候进得去？

<figure class="diagram">
<!--@include: ./figures/turn-loop-1.svg-->
<figcaption>三家的循环骨架是同一条，差别在三个外部入口各自被允许作用在哪里。插话三家一致地只在轮顶生效；中断则跨两个位置，而这两个位置的善后完全不同——左边是「话说了一半」，右边是「事可能已经做了一半」。</figcaption>
</figure>

::: codex 队列加一个交付相位 | 全量源码
- 队列里的输入有三种：用户输入、注入的响应条目、**代理间通信**
- 排空这个队列的时机**在两处刻意延后**：回合刚开始时（让新鲜输入先被采样），以及自动压缩之后（让模型或工具的续跑先恢复）
- 另有一个 `MailboxDeliveryPhase` 状态机：回合一开始是 `CurrentTurn`，一旦记录了用户可见的终态输出就切到 `NextTurn`——**晚到的子代理信件不去延长一个已经显示完的答案**；如果这个任务又拿到显式的同轮工作就重开

来源：`core/src/session/input_queue.rs` · `core/src/state/turn.rs`
:::

::: ours 注入点定在三处约束的交点 | 本仓源码 · ADR-0090
- 位置：轮顶、三道闸**之后**、`runStep` **之前**
- 在 `runStep` 之前，所以这一步的计量与压缩阈值看到的就是含它的那份历史
- 在三道闸之后，所以撞上任何一道时那句话仍留在收件箱里——**没有一句话会落进一个不会再读它的 Run**
- Esc 不新开机制，它只是让这个边界提前到来
- 对标证据是从真机转录里挖的：入队到出队 **552 毫秒**，贴着上一个工具结果注入，assistant 那一轮没有中断

来源：`docs/decisions/0090` · `contracts/run-inbox.ts`
:::

::: info 另外两家 — 档 B / 全量源码
- **Claude Code**：结果消息带一个 `origin`，让流式输入的消费者分得清「这是我自己那句 prompt 的结果」还是「这是后台任务通知注入的一轮」
- **dsh**：驱动器的说明是「队列化的回合与**步边界输入**」，待办输入放在一个 `Inbox` 里，而 Inbox 被定义成「持久待办工作的、代理拥有的投影」

来源：`types.py` · `core/agent-loop/src/agent.ts`
:::

::: tip 同构
四家（含本仓）撞出同一条：**插话只在边界注入，没有一家往流中间插**。这条不是性能取舍，是正确性——一次请求已经发出去了，改它的输入只能靠取消重发。

codex 那个交付相位是本仓没有的一格，但触发条件本仓也具备：子代理跑完回话的时机不受控，如果它落在一个已经给出终态答案的回合上，用户会看到答案后面莫名其妙又续了一段。
:::

## ⑤ 中断的时序

取消信号要传到在飞的模型请求、在跑的工具、在等的审批。这三件事谁先谁后？

这一维最有说服力的一句话来自 codex，而且它在同一个文件里被写了两遍——一次在 `abort_all_tasks`，一次在 `abort_turn_if_active`：

> Let interrupted tasks observe cancellation before dropping pending approvals, or an in-flight approval wait can surface as a model-visible rejection before TurnAborted.
>
> —— `core/src/tasks/mod.rs`

翻译过来：**先让被中断的任务观察到取消，再丢掉待处理的审批**。顺序反了的话，一个在途的审批等待会先变成「模型看到的拒绝」，`TurnAborted` 才姗姗来迟——于是模型的历史里多出一条「用户拒绝了这次调用」，而用户其实只是按了 Esc。这种 bug 不会让任何测试变红，它只会让模型在下一轮里道歉。

::: codex 取消令牌 + 封闭原因 + 清空等待者 | 全量源码
- 每个运行中的任务持有一个 `CancellationToken` 与一个「丢弃即中止」的句柄
- 回合状态里有五类待处理等待者：审批、权限申请、用户输入、MCP 征询、动态工具，一个 `clear_pending_waiters()` 一次清空
- 中断之后如果队列里还有活，会**顺手起一个新回合**（只在 `Interrupted` 这一档）

来源：`core/src/tasks/mod.rs` · `core/src/state/turn.rs`
:::

::: dsh 取消原因分四种来源 | 全量源码
- `AgentCancelCause`：`user` / `parent` / `hook`（带理由）/ `disposed`
- `parent` 是父代理取消子代理——**这是子代理体系必须有的一格**
- 持久化那一侧还多一个 `legacy`：导入的旧记录没有原因，给它一个专门的值，而不是让原因变成可选字段

来源：`core/session/src/types.ts`
:::

::: claude 中断是控制请求，不是信号 | 档 A（SDK 侧）
- `interrupt()` 走控制通道发一条 `{"subtype": "interrupt"}`，**只在流式模式下有效**
- 同一条通道还能中途改权限档、换模型
- SDK 的取消信号位在类型里留着，但注释写明**目前恒为 None**——这一格是留位不是实现

来源：`_internal/query.py` · `client.py:278`
:::

::: warning 分岔 · 本仓的这一格有实测数字
本仓 ADR-0089 解决的正是这条链上最后一段缺口：信号此前一路传到了每个工具与审批网关，**唯独模型调用上没有信号位**。后果是按下 Ctrl+C 要等模型把话吐完，真机实测 **44–75 秒**，那段输出的 token 照付。

修法是把信号位加成 `ModelGateway.invoke` 的**必填**参数。理由写得很硬：「新调用点忘了传」没有任何症状，而症状恰好是「Ctrl+C 不生效」。加参数只对调用点是编译错误——而调用点正是要守住的那一半。
:::

## ⑥ 中断之后，模型看到什么

这一轮被掐断了。下一轮开始时，模型的历史里留着什么？这决定了它接下来的第一反应。

这是三家里本仓做得最细的一维，而且理由有实验数据支撑，所以这一节反过来讲：先说本仓，再看另外两家在同一件事上做了什么。

::: info
掐断时那条流已经吐出来的半句正文不能丢：丢了则这一轮在历史里没有任何痕迹，下一轮模型不知道刚才发生过什么。但留下就有一个新问题——**没闭合的 `tool_use` 要补占位结果，否则出站消息里这一对配不上，端点直接 400。**

本仓的落地是一张 `stop → 措辞` 的表，三档：`pause_turn` / `max_tokens` / `aborted`。做成表而不是三元链，是因为**加第四档时少写一句措辞会当场编译不过，而措辞是模型唯一读得到的东西。**

掐断那一档的措辞是「这次调用没有派发：用户中断了这一轮。」，两个刻意的取舍：

- **说「没有派发」而不是「可能已经执行了一半**」。模型调用排在工具派发之前，被掐时一个调用都没派发出去，这是可证明的事实。后一种口径成立的是「工具轮中途被掐」那一格，而那一格不走这条路径。
- **不带「仍然需要的话请重新提出」**，另两档都带。用户是故意叫停的，接下来说的话才算数。重放数据很直接：**带引导 0/3，只留标记 3/3**——任何把模型往「接着做」推的句子都会让它无视新指令。
:::

::: dsh 同一个动作，另一个入口 | 全量源码
- 中止时调度器**为被跳过的调用记录合成错误结果**，错误码 `TOOL_ABORTED_BEFORE_DISPATCH`，理由写明是「好让重放保持有效」
- 它在崩溃恢复那条路上也做同一件事（`interruptedTurnClosers`，见上一份对读的 ⑤）
- 也就是 dsh 在**中断与崩溃两个入口上用了同一个答案**

来源：`core/agent-loop/src/tool-calls.ts`
:::

::: codex 事件层面留痕 | 全量源码
- 中止发一条带原因的回合中止生命周期事件，那四个值就是给这里用的
- 历史层面靠执行标记本身落盘（`Compacted`、`TurnContext` 那一组），恢复时按条目重放
- 没有找到与本仓「占位措辞」等价的东西——**这一格可能存在但我没核到**

来源：`core/src/tasks/mod.rs`
:::

::: claude 停在可观测面 | 档 B
- `aborted_streaming` 与 `aborted_tools` 说明它内部区分了这两格
- 但中断后写进本地 JSONL 的到底是什么形状，**不可读**

来源：`types.py`
:::

::: warning 分岔 · 且它修正了上一份对读的一句话
上一份《会话持久化与恢复》⑤ 里我写：dsh 补一条假的结果让历史合法，**本仓丢掉整步让模型重问**。那句话对崩溃恢复成立，对中断不成立。准确的说法是：**本仓两条路各有一套——中断路径上补占位结果（三档措辞），崩溃恢复路径上丢掉整步。**

两条路的判据其实是自洽的：中断时循环还活着，「一个调用都没派发出去」是可证明的事实，所以能写一句准确的话；崩溃后循环已经死了，那一步的记录本身都可能没落，重放出来的结果无处可去。**知道发生了什么就补齐，不知道就别编**——与 ③ 里 dsh 那对相反的处置是同一条判据。
:::

## ⑦ 失败分类与重试

模型调用失败、工具报错、装配抛异常——这三件事在循环眼里是不是同一件事？

::: ours 三类，处置各不相同 | 本仓源码
- **带内失败**（触顶限额、模型 refusal / max_tokens）：落终态、发事件、正常返回。**这是 Run 的一种结局，不是程序出错**
- **带外错误**（装配抛错、store 抛错、provider 违约）：按**这一步派发过工具没有**分档。派发过的直接上抛、不转成事件、Run 留在 `running`——此刻并不知道世界变没变，谎报一个 `failed` 比留着 `running` 更糟
- **一次工具调用不成立**（幻觉的工具名、参数不合 schema、工具自己报错）：既不终止也不上抛，归一成 `is_error` 的结果喂回模型

来源：`core-runtime/src/loop/agent-loop.ts`
:::

::: dsh 恢复权交给一个监听器 | 全量源码
- `RequestErrorAction = { kind: 'retry' } | undefined`——**模型请求的恢复由一个插件拥有，它只能说「重试」或「不管」**
- `TurnEndReason.error` 带的永远是结构化失败：要么是提供方错误的事实原样，要么是扁平化的 `{ message, code: 'UNKNOWN' }`
- 重试本身是日志事件：`llm/retry` 与 `llm/retry-started` 各占一个已知事件类型

来源：`core/agent/src/runtime-types.ts` · `core/session/src/known-event-types.ts`
:::

::: claude 错误码进结果消息 | 档 B
- 结果消息带 `api_error_status`：失败那次 API 调用的 HTTP 状态码（429 / 500 / 529）
- 注释特意写明「**可以安全记录，不含消息内容**」——一个把敏感度写在类型注释里的例子
- 另有 `permission_denials` 与 `errors` 两个列表

来源：`types.py` · `ResultMessage`
:::

::: tip 同构
三家都把重试与失败做成**可观测的事实**，而不是埋在循环内部的一段 `for`。dsh 让它占两个事件类型，Claude Code 把状态码放进结果消息并标注可安全记录，本仓的 `#124` 也是「有上界的重试，且重试过程是事件」。

本仓那条「按派发过工具没有分档」是三家里唯一把「**不知道世界变没变」当成一种独立处置**的。另外两家的错误分类都停在「是什么错」，没有回答「这个错允不允许我下结论」。
:::

## ⑧ 上界：轮次、token、钱、时间

「别让它跑太久」有四种量法，而三家各自只量了其中几种。

| 量什么 | Claude Code | codex | deepseek-harness | 本仓 |
| --- | --- | --- | --- | --- |
| 轮次 | `max_turns` | 无固定上限 | 无固定上限 | `maxSteps`，未填即不限 |
| 输出 token | `max_thinking_tokens` 等 | 模型侧上限 | `max-tokens` 是一种回合终态 | `max_tokens`（四种预算里的第 ③ 种） |
| 累计花费 | **`max_budget_usd`，按美元** | `BudgetLimited` 是一种中止原因 | 未核到 | 任务预算按 token，70/90 两档告警 |
| 单次工具耗时 | bash 超时转后台 | 后台终端 | **协作式超时插件** | 120 秒总时长，超时停 Run |

两处值得展开。**Claude Code 是唯一按钱设闸的**：超了返回一个 `error_max_budget_usd` 结果。另外两家和本仓都按 token，而 token 与钱的换算是随模型变的——本仓 §9.6 把「预算」这个词拆成四件事（账户额度、任务预算、单次输出上限、装配预算），其中账户额度那一档明写「端点不暴露查询接口，只能撞上去」。

**dsh 的超时是协作式的，这一格设计得很干净**。工具声明自己的 `timeoutMs` 并**承诺尊重取消信号**，插件只负责武装那个截止时间，「不与工具的 promise 赛跑、也不抛弃它」。而 `TOOL_TIMEOUT` 这个码同时是内部分类码和替换结果上的结构化错误码，作用范围被特意限定在自己身上——理由是**不要把外层某个先触发的截止时间误读成自己的超时**，那种情况应该读成一次普通的上游取消。

::: warning 分岔
本仓的任务预算有一格是另外两家都没有的：**越过阈值时给模型追加一条提示**——也就是模型*知道*自己快没钱了。另外两家的上界对模型都是不可见的硬闸。这个差别在长任务上会体现成不同的行为：知道预算的模型会开始收尾，不知道的会被从中间切断。
:::

## ⑨ 原地打转

模型第四次调用同一把工具、同样的参数。谁该管这件事，怎么管？

《上下文管理》那一份的 ⑦ 讲过压缩层面的死循环（压完还是满，再压，无限循环），三家给了计数停机、不设闸、单调量三个答案。这里是另一个死循环：**循环本身在原地打转，而每一轮都在调模型。**

::: dsh 递进提醒，不否决 | 全量源码
- 一个咨询性的连续重复调用检测器，默认阈值 **`[3, 5, 8]`**——**不是一次掐断，是三次递进的提醒**
- 它**不否决也不改写调用**，只往模型上下文里塞一条提醒
- 配置错误一律在插件加载时抛错（空阈值列表、非整数、小于 2、重复值），注释写明「绝不静默回退」
- 提醒里引用的参数截到 500 字符，理由很妙：**大 payload 恰恰会在循环场景里无界地骑进下一次请求**；上限管的是提醒，不是检测——比对用的永远是完整字符串
- 提醒被打上「插件」来源标记，注释说这个标签是承重的：没标签的上下文会在派生历史里**渲染成一条用户提示**

来源：`guard/repeat-tool-reminder/src/index.ts`
:::

::: ours 问「这一轮有没有产出」 | 本仓源码
- 判据是 `producesNoMessage`：这一轮有没有往对话日志里写进任何东西
- 关键在于它**问的是消息不是文本**：思考不进日志，所以「只吐了 thinking 的一轮」在模型眼里与什么都没发生一样，**装配出的下一个请求与上一轮逐字相同**
- 判成「有产出」就会一路空转到触顶步数上限
- 不自己数字段而是复用同一个函数，理由是「什么算产出」只能有一个答案

来源：`core-runtime/src/loop/run-turn-algebra.ts`
:::

::: info 另外两家 — 全量源码 / 档 B
- **codex**：没找到工具层面的重复检测。它在压缩那一维上明确选择了不设闸（「只要压缩管用，就不该担心死循环」），工具层面**是不是也一样，我没核到**
- **Claude Code**：`max_turns` 是硬闸。按它自己的 turn 定义，那道闸拦的是「一问一答」的次数，**拦不住一轮里连调三十次工具**

来源：`—`
:::

::: warning 分岔 · 四个答案
递进提醒（dsh）、单调量判据（本仓）、硬闸（Claude Code）、不设闸（codex）。四者的代价各不相同：提醒最温和但要求模型听劝；单调量最严谨，但只拦得住「完全没产出」，拦不住「有产出但在绕圈」；硬闸简单，但拦的量纲可能不对；不设闸的失效方式是烧钱。

本仓这一格其实**只有半格**：`producesNoMessage` 拦的是空转，而「连着三次读同一个文件」是有产出的空转，它拦不住。dsh 那个阈值 `[3, 5, 8]` 加咨询性提醒，是本仓可以直接照抄的形状——它不动循环的任何判决，只加一条上下文。
:::

## 对本仓意味着什么

### 同构 —— 三家都这么做，可以当定论

- **插话只在边界注入**。没有一家往在飞的请求里插，本仓 ADR-0090 已在这条线上。
- **「为什么停」是封闭取值域**。本仓做得更细一格：取消不带失败码。
- **工具结果按模型给的顺序回填**。并发只影响派发，不影响顺序。
- **重试是可观测事件，不是内部循环**。三家一致。

### 本仓没有 —— 补不补是决策，本文不作

- **「新回合顶掉旧回合」这个概念**。codex 的中止原因里 `Replaced` 单独占一值。M2 有 server 之后，同一个 Session 上来两条请求会发生，而现在它只会撞上「这个 Session 已经有活动 Run」的拒绝。
- **晚到消息的交付相位**。子代理回话的时机不受控，落在一个已经给出终态答案的回合上，用户会看到答案后面又续了一段。codex 的两态状态机是现成形状。
- **有产出的绕圈**。本仓的空转判据拦不住「连着三次读同一个文件」。dsh 的递进提醒不动循环的任何判决，只加一条上下文，是最低成本的补法。
- **工具声明自己的超时**。本仓是统一的 120 秒总时长；dsh 让工具自己声明并承诺尊重信号，超时结果带结构化错误码可供路由。

### 三家分歧 —— 要自己判，没有现成答案

- **上界按什么量**。只有 Claude Code 按钱。本仓按 token 且让模型知道，这个「让模型知道」是本仓独有的一格，长任务上会表现成不同的收尾行为。
- **并发的准入判据**。本仓最保守，且保守的理由（分组必须早于风险判定）是另外两家没有的约束——它们的风险判定不读参数。
- **压缩算不算一个回合**。codex 给它一个槽位，另外两家不给。这个选择会传导到界面上：压缩要不要显示成一步。

## 证据档次与没核到的部分

codex 与 deepseek-harness 是全量源码，每一条都能落到文件与行号；引号里的话是头注释原文的转述。**Claude Code 这一份里档次最低**——循环本体在 CLI 引擎里不可读，可读的只有 SDK 暴露的那一圈形状。凡是写「未核到」的格子都是真的没读到，不是省略。

### 明确没核到的

- Claude Code 的循环骨架、并发策略、中断后的历史形状——三格全空
- codex 有没有工具层面的重复调用检测（压缩那一维它明确选择不设闸，工具层面是不是同一个态度，没读到）
- codex 中断之后写进历史的占位形状，与本仓那三档措辞是否有对应物
- dsh 有没有按金额的上界
- 三家都没有跑起来做行为实测；本仓那两个数字（44–75 秒、552 毫秒）是本仓自己的真机记录与对标转录，不是这一轮测的
