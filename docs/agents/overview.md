# 智能体功能简介

## 先说清楚：智能体是什么

一个编程智能体由两部分组成：**模型**，和**包在模型外面的一圈程序**。模型只会输出文字，其中一种文字是「我要调用某个工具，参数是这些」；真正去读文件、跑命令、发网络请求的，是外面那圈程序。Claude Code 的官方文档把这圈程序叫作 agentic harness（智能体框架）。

同一个模型，换一圈程序，能力会差很多：这圈程序决定了模型能用哪些工具、每一轮能看到什么、哪些操作要先问人、跑到一半出错了怎么办。这个分类讲的就是这圈程序。

本页把 Claude Code、codex、deepseek-harness 三家的功能整理成 8 组 29 项，每项讲两件事：它是什么，难在哪。清单依据三家的一手资料：[Claude Code 官方文档](https://code.claude.com/docs/en/overview)、[codex 官方文档](https://developers.openai.com/codex)与[开源代码](https://github.com/openai/codex)、[deepseek-harness 开源代码](https://github.com/deepseek-ai/deepseek-harness)与子系统文档，核对日期 2026-10-11。已经有三家对照文章的项，末尾列出了链接。

## 一、核心循环

### 回合循环与中断

模型想一步，要调工具就去调，把结果交还给它，再想下一步，直到它认为做完了：这个循环是所有智能体的骨架。循环跑的时候，用户可以按 Esc 打断，也可以直接补一句话让它调整方向。

<small>难点</small> 骨架一句话说得完，难在缝隙里。一个「回合」怎么算（用户敲一次回车，还是模型调一次工具），决定了「最多跑几轮」这道闸拦在哪里；用户中途插的话必须落在合适的边界上，否则模型会看到一份前后矛盾的历史；按下 Esc 时，取消信号要按正确的顺序传给在飞的请求、在跑的工具和在等的审批；「停下」有跑完、被叫停、预算用完、出错、原地打转好几种，事后要分得清。

延伸阅读：[Claude Code](/agents/claude-code/turn-loop)、[codex](/agents/codex/turn-loop)、[deepseek-harness](/agents/deepseek-harness/turn-loop) 各自的回合循环与中断，[三家差异](/agents/turn-loop)

### 模型接入

用哪个模型、推理强度开多大，请求发给哪家服务商或企业网关，出错了怎么重试，用了多少怎么记账。

<small>难点</small> 发一个 HTTPS 请求不难，难在失败和差异都发生在对面：发错一个字段可能照样返回成功，流式输出可能吐到一半就停住，限流可能等一会儿就好，也可能是这个月的额度没了，三种情况在传输层看起来差不多。这一层要决定哪些差异在内部消化掉，哪些必须告诉上层。

延伸阅读：[模型接入层](/agents/model-access)

## 二、工具

### 工具调用机制

模型自己不动手，它只输出一段结构化的请求：「调用某个工具，参数是这些」，由外面的程序去执行。每个工具的名字、用途和参数格式，要事先写成说明交给模型。

<small>难点</small> 工具说明本身就占上下文：接了几十个工具，每一轮请求都要带上全部说明。于是出现了几种做法：全部说明一开始就给；先只给名字，模型要用时再搜出完整说明；或者让模型写一段代码，在代码里一次调用多个工具。几种做法的差别在于说明什么时候进上下文、下一步调什么由谁在什么时候决定，以及审批卡在哪一步。

延伸阅读：[工具调用的三条路](/agents/tool-calling)

### 文件读写与搜索

读文件、改文件、建新文件，按文件名或内容在代码库里搜索。这是编程智能体用得最多的一组工具。

<small>难点</small> 模型手上没有文件，只有几轮之前读到的一份副本，这份副本可能已经过时。它描述的修改要落到真实文件上，需要一个坐标：用行号，改完一处后面的行号就变了；用原文片段，又要求这段文字在文件里唯一。换行符和编码处理不当，改一个词会让整个文件每一行都显示为改动。写入不可逆，所以这组工具最需要「宁可拒绝也不要猜」。

延伸阅读：[文件工具的语义](/agents/file-tools)

### Shell 执行

让模型跑终端命令：编译、测试、装依赖、用 git。

<small>难点</small> 普通工具调用是「发请求、等结果」，命令不是这个形状：`ls` 几毫秒，`pnpm install` 几分钟，`npm run dev` 永远不返回；输出可能大到撑满上下文；shell 有状态（`cd`、`export`）；子进程会继承一切，包括智能体自己的 API key；有的命令还会停下来等人输入密码，而终端前面没有人。一条命令跑太久时谁来决定、怎么决定，最能看出各家的设计取向。

延伸阅读：[命令跑起来之后](/agents/shell)

### 联网搜索与抓取

搜网页、抓取文档页面，用来查报错信息和最新的接口文档。

<small>难点</small> 网页是外部输入，可能夹带「忽略之前的指令」这类文字，模型读到后有被带偏的风险；网页又大又杂，要先转成模型能读的文本、截到合适的长度；在企业环境里，还要能限定可以访问哪些域名。

### 代码智能

接入语言服务器（LSP，编辑器里「跳转到定义」「标红类型错误」背后的那套服务），让模型按符号查找定义和引用，改完代码马上看到类型错误。

<small>难点</small> 每种语言要单独的语言服务器，启动慢、占内存；它报回的诊断信息要挑重点交给模型，否则又是一大段噪音。好处是按符号查找能代替大范围读文件，反而省上下文。

### 浏览器与电脑操作

让模型操作浏览器测试网页、读控制台日志，或者直接看屏幕、点鼠标、敲键盘，操作桌面程序。

<small>难点</small> 这类操作的影响面比改文件大得多（点下去的可能是「付款」或「删除」），多数无法撤销；屏幕截图很占上下文；网页和屏幕上的内容同样可能夹带指令。所以通常要配更严格的确认和隔离。

## 三、上下文与记忆

### 上下文管理与压缩

模型没有记忆，每一轮都要把整段对话重新发给它；它一次能读的量有上限，叫上下文窗口。窗口快满时，常见的做法是先清掉旧的工具输出，不够再把前面的对话压成一段摘要。

<small>难点</small> 撑满窗口的主要不是聊天，是工具输出：读一个三千行的文件、跑一次测试，几千行就进去了。什么时候压、在哪一步压、摘要写成什么样都有讲究，压坏了会丢掉关键约定。还有一种失效：一个超大的输出让窗口压完又立刻满，自动压缩陷入死循环，每一轮都在花钱调模型。

延伸阅读：[Claude Code](/agents/claude-code/context)、[codex](/agents/codex/context)、[deepseek-harness](/agents/deepseek-harness/context) 各自的上下文管理，[三家差异](/agents/context)

### 提示词装配与缓存

一次请求由十几个来源拼成：智能体的身份说明、工具说明、项目指令、当前权限、环境信息、对话历史。谁来拼、按什么顺序拼，归这一项管。

<small>难点</small> 服务商的提示词缓存按前缀匹配：从开头逐字比对，遇到第一处不同，后面的全部重新计算。所以把「当前时间」写进系统提示词，代价不是多几个字，而是每一轮都按全价重来。会变的东西放在哪、变了怎么告诉模型、缓存什么时候被打破，都要专门设计；而且缓存失效是静默的：账单涨了，功能一切正常。

延伸阅读：[别动前缀](/agents/prompt-cache)

### 项目指令文件

仓库里的一份说明文件（Claude Code 叫 `CLAUDE.md`，codex 叫 `AGENTS.md`），把「这个项目怎么干活」直接告诉模型：用什么命令构建、有哪些约定、哪些事不能做。

<small>难点</small> 看起来是读一个文件，实际要回答一串问题：仓库的、用户全局的、公司下发的几份怎么合并；子目录里的那份什么时候读；文件太大怎么办；文件里引用的其他文件跟不跟；克隆来的陌生仓库，它的说明文件读不读（这是第一段能对模型说话的攻击面）；跑到一半文件改了怎么办。

延伸阅读：[仓库自己写的规矩](/agents/project-instructions)

### 跨会话记忆

每开一个新会话，模型就失忆一次。记忆功能让智能体自动记下用户的偏好和项目经验，下次会话开始时再带回来。

<small>难点</small> 写什么由模型判断，而模型会判断错，把一次性的讨论当成长期偏好记下来；只增不减会变成杂乱的日志，前后矛盾也没人发现；记忆会被注入到之后的每个会话里，写进去一次密钥就等于泄露无数次。三家在这一项上连立场都不同：有的做成内置服务，有的明确认为这件事不该由智能体框架来管。

延伸阅读：[谁替你记得](/agents/memory)

### 会话持久化、恢复与回退

把对话和每一步操作写到磁盘上：关掉之后能接着聊，能从某一点分叉出一个新会话，也能把文件改动退回到之前的状态。

<small>难点</small> 进程最可能死在「工具已经发出去、结果还没回来」的时候，于是日志末尾常挂着一个没有结果的工具调用，而服务商不接受这样的历史：读回来不等于能接着跑。日志有两个读者，模型要一段合法的对话，人要知道当时到底发生了什么。写盘本身也会失败。「回到原处」既可能是回到崩溃前，也可能是回到三轮对话之前，后者对存储格式的要求苛刻得多。

延伸阅读：[会话持久化与恢复](/agents/session)

## 四、任务编排与多智能体

### 待办与计划模式

待办清单让模型把任务拆成几步，边做边勾，用户能看到进度。计划模式让模型先只读、出方案，用户批准后再动手。

<small>难点</small> 清单的格式三家已经很接近，真正要选的是规矩放在哪里：写在工具说明里让模型自觉遵守，还是由程序校验。计划模式看起来是产品形态，实际是一道权限题：「只读、不许改」是靠一句提示，还是由权限系统强制，三家给出了从软到硬的一整条光谱。

延伸阅读：[编排层](/agents/orchestration)

### 目标、后台任务与定时

目标：给出一个完成条件，让智能体一直跑到条件满足。后台任务：把长时间的命令或子代理挪到后台，做完再通知模型。定时：到点自动发起一次任务。

<small>难点</small> 「自己接着跑」必须有闸：按轮数、token、时间还是钱来限制，用完了是停下还是拒绝。不在当前这一轮里发生的事（后台做完了、时间到了），要找到合适的时机进入对话，而且不能打断正在进行的那一轮。

延伸阅读：[编排层](/agents/orchestration)

### 子代理

主智能体派出一个新的智能体去完成子任务。它在自己独立的上下文里干活，最后只把结论带回来，主对话不会被中间过程撑满。

<small>难点</small> 子代理不是一个线程，而是一个会自己做决定的对象。派出时带走多少上下文：不带要从零摸索，全带就失去了隔离的意义。派出之后还能不能追问、改主意、让两个子代理互相看结果。最危险的是授权：用户在主对话里同意了「把这个目录清干净」，子代理要执行删除时，它手上并没有那句同意，它该去问谁？

延伸阅读：[子代理的协作语义](/agents/subagent)

### 多智能体协作与并行

不止一个子代理：几个智能体分工合作、互相发消息、共享任务列表，或者由模型写一段脚本批量调度几十个子代理；再配合 git worktree，让几个会话在各自的目录里并行改代码，互不干扰。

<small>难点</small> 多个智能体同时动同一个仓库会互相踩，要么隔离目录，要么协调分工；它们之间的消息、任务依赖和结果汇总都需要有地方存；并行得越多，花钱越快，出了错也越难追查是哪一个干的。

## 五、安全

### 权限与审批

决定哪些操作可以直接做、哪些要先问用户、哪些一律禁止。用户可以写规则（比如允许 `npm test`、禁止改 `.env`），也可以切换模式（每步都问、只问命令、全自动）。

<small>难点</small> 权限判定看的是模型「说」它要做什么，而同一件事可以换个写法、换层包装，绕过名单：判定器一定有漏判的形状。审批时能不能改写参数、能不能让另一个模型代替人来批、规则放在哪里，三家各有各的答案。

延伸阅读：[沙箱与权限的三种解法](/agents/sandbox)

### 沙箱隔离

用操作系统自带的隔离机制，限制命令能读写哪些目录、能不能联网。即使权限判定放行了，命令也只能在划定的范围里动。

<small>难点</small> 如果说权限判定是门口的保安，沙箱就是屋子本身的锁：保安可能被话术绕过，锁只认系统调用，程序自己也拆不掉。代价是每个操作系统的锁都不一样（macOS、Linux、Windows 各要一套），有些门确实锁不住；命令被锁住而失败时，还得给模型留一条体面的退路，让它知道该申请放宽，而不是反复重试。

延伸阅读：[沙箱与权限的三种解法](/agents/sandbox)

### 凭证与身份

智能体怎么登录、调用模型的密钥存在哪里，模型和它启动的程序能不能看到这些密钥，以及服务端能不能认出「这是某个智能体代表某个人在跑某个任务」。

<small>难点</small> 这其实是三道题。智能体自己怎么认证，三家做法差不多；模型能碰到什么是最大的分歧：子进程默认继承环境变量，一句 `echo $ANTHROPIC_API_KEY` 就能把密钥打印进对话；智能体算不算一个独立身份，三家回答的根本不是同一个问题。只解第一道题，密钥存得再好，也挡不住模型去读 `~/.aws/credentials`。

延伸阅读：[凭证与身份](/agents/credentials)

## 六、扩展

### 钩子

在固定的时机（调用工具之前和之后、会话开始、用户提交输入等）自动执行一段用户写的脚本，用来格式化代码、记日志、发通知，或者拦下危险操作。

<small>难点</small> 钩子是别人写的代码在你的机器上跑，而且它恰好位于权限判定之前：一个能在「调用工具前」放行的钩子，等于一把绕过审批的钥匙。钩子能返回什么、说了算多少（只能拦、还能改、还能往上下文里加话），需要一套明确的协议。

延伸阅读：[扩展面](/agents/extensions)

### 技能、斜杠命令与插件

技能是一包「这类活该怎么干」的说明，平时只占一行描述，用到时才读入全文；斜杠命令让用户敲一行 `/xxx` 直接触发某件事；插件把技能、命令、钩子、MCP 打成一个包，可以通过插件市场分发给别人。

<small>难点</small> 它们都要挤进同一个上下文窗口，每多一条常驻描述，正事就少一分预算，而扩展是「装上就不再想起」的东西，成本会悄悄增长。一旦有第二个用户，配置就有了层级：系统、企业、用户、项目、插件，谁能覆盖谁、谁只能收紧，都要说清楚。从陌生来源装来的插件默认信不信任，也是必须表态的问题。

延伸阅读：[扩展面](/agents/extensions)

### MCP

MCP（Model Context Protocol，模型上下文协议）是接外部工具和数据的标准协议：数据库、Slack、浏览器、公司内部系统，各自做成一个 MCP 服务，智能体连上就能用它提供的工具。

<small>难点</small> MCP 工具不是自己写的，而是一个陌生进程报上来的一条描述：名字可能和别的工具重名；接三个服务可能就多出四十个工具，全塞给模型等于把上下文预算交给别人花；「这个工具危不危险」的标记由服务自己填写；服务还能反过来向用户提问、读目录、借用你的模型。后两点等于把一部分决策权交给了一个你没写过的程序。

延伸阅读：[接进来的工具算谁的](/agents/mcp)

## 七、运行形态与集成

### 使用界面

在哪里用智能体：终端、IDE 插件、桌面应用、网页、手机。同一个智能体往往有好几种界面，底下的循环和工具是同一套。

<small>难点</small> 界面和内核如果不在一个进程里，中间就要有一条协议（见下一项）。终端界面还要处理滚动、重绘、键盘输入这些老问题，长会话里的闪烁和卡顿很影响体验。几个界面同时连着一个会话时，审批该弹给谁也要有规则。

延伸阅读：[屏幕归谁管](/eng/terminal-screen)（工程笔记）

### 非交互运行、SDK 与协议

不开界面，在脚本或 CI 里直接跑一个任务（比如 `claude -p`、`codex exec`）；把智能体当作库嵌进自己的程序（SDK）；或者通过一套进程间协议，让别的界面来驱动它的内核。

<small>难点</small> 这条线是双向的：事件从内核流向界面，但审批要由内核发问、界面回答，这就需要请求编号、超时、取消和断线处理。往线上推多少也要权衡：推少了界面画不出过程，推多了敏感内容跟着出去。最难的是升级：内核和界面各自发新版本时谁负责不出错，而出错的方式往往不是崩溃，是悄悄读错。

延伸阅读：[进程之间那条线](/agents/protocol)

### 云端与远程执行

把任务交给云端的机器去跑，人离开电脑也能继续；或者在本机开会话，从手机或浏览器远程操控；也可以让智能体通过 SSH 在另一台机器上执行。

<small>难点</small> 云端环境要能装好项目依赖、拿到代码仓库的权限，又要限制它的网络访问；任务跑完后，结果要能拉回本地接着改。本地和云端之间来回切换时，会话、文件改动和权限设置都要能跟着走。

### 代码审查

让智能体审查本地改动或一个 PR，找出逻辑错误、安全漏洞和回归问题，审查过程本身不改代码。

<small>难点</small> 审查的价值在于查得准，误报多了就没人看了，常见做法是让几个智能体从不同角度各审一遍，再交叉核对结论。它还要拿到足够的上下文（改动牵涉到的其他代码、项目的约定），而不只是看 diff 本身。

## 八、企业与运维

### 配置分层与托管策略

设置分为几层：用户全局、项目、本机、公司统一下发。管理员可以通过托管策略强制某些设置，比如只允许用指定的模型、禁用某些 MCP 服务、关掉钩子。

<small>难点</small> 「谁的设置优先」不够用。管理员真正要的不是「我的值盖过你的」，而是「你选不到那个值」：前者是覆盖，后者是收紧。只做了覆盖的配置系统，用户总能改一个管理员没写过的字段，把自己调到策略之外。

延伸阅读：[企业部署面](/agents/enterprise)

### 遥测、计量与成本

把运行数据（用了多少 token、调了哪些工具、出了什么错）导出到公司的监控系统，统计每个人、每个团队花了多少钱。

<small>难点</small> 遥测是产品唯一一处主动把用户的东西往外发的地方，而在编程智能体里，「用户的东西」恰好是提示词、代码和工具输出：默认发不发、发多细、发给谁，是三个独立的决定。费用还要能按公司谈下来的价格计算，厂商标价对内部结算没有意义。

延伸阅读：[企业部署面](/agents/enterprise)
