# 工具调用的三条路

<Badge type="info" text="agent-platform · 技术盘点" />

传统 `tool_use`、codex 的 Code Mode、Claude Code 的 Tool Search——同一道题「模型怎么使唤工具」的三个不同答案。它们分歧的不是「谁动手」，而是「下一步该干什么，在哪一刻、由谁决定」。

核验日期 2026-08-24 · Code Mode 一节 2026-08-25 复核 · 上游会改版，引用前先看日期 · 本页不定义 § 锚点、不构成决定

## 模型从不亲自动手

<Badge type="info" text="共同前提" />

``

三条路径都建立在同一件事上：**模型输出的永远只是文本或结构化数据，它自己不执行任何动作**。真正去查数据库、跑命令、发请求的，是包在模型外面的那层程序——本项目里叫 runtime，codex 里叫 `Session` / `ToolCallRuntime`，Claude Code 里就是 CLI 客户端本身。下文统称 **agent**。

这条前提在三条路径里都成立，包括 Code Mode——模型在那里写的 JS 代码，调用的也只是 agent 预先挂进执行环境的那几个函数，它碰不到真实的数据库句柄或网络套接字。

既然「谁动手」是相同的，差异就只能出在别处。真正的分歧有三个：

1. **工具的说明书（schema）什么时候进上下文**——全量前置、还是按需装载。
2. **「下一步调哪个工具」这个决定在哪一刻做出**——每步问一次模型、还是模型一次性把整段流程写死。
3. **风险判断与审批卡在哪个节点上**——卡在「模型每提一次请求」，还是卡在别处。

## 传统 tool_use

<Badge type="info" text="路径一 · 业界默认" />

``

模型在响应里发出一个 `tool_use` 块（工具名 + 参数），然后**停止生成**；agent 收下、执行、把结果作为 `tool_result` 塞回消息列表，再发起**新一次模型调用**；模型看到结果，决定下一步。循环往复，直到模型不再要求调用工具。

全部可用工具的完整 schema 挂在请求的前缀部分。这有两个后果：工具一多，光 schema 就吃掉大量上下文；而工具集一旦在会话中途增删，整条缓存前缀作废（本项目 §9.3 明确记了这一条，也正是它推向静态裁剪的理由之一）。

**任务：查销量 → 算总和 → 发邮件** · 加粗行 = 一次模型往返

| 谁 | 做什么 |
| --- | --- |
| **模型** | **输出 `tool_use: 查数据库`，停止生成<br><small>此刻上下文里挂着全部工具的 schema</small>** |
| agent | 风险判定 → 审批（如需） → 执行 → 审计留证 |
| **模型** | **看到销量数据，输出 `tool_use: 算总和`** |
| agent | 同一套四段式，执行 |
| **模型** | **看到总和，输出 `tool_use: 发邮件`** |
| agent | 同一套四段式，执行 |
| **模型** | **输出最终答复** |

模型往返：**4 次**　·　每次都重新携带全量 schema　·　每个动作都被单独检查过一遍

三步任务在传统模式下的开销结构。往返次数 = 工具调用次数 + 1。

### 它贵在哪、又值在哪

贵在两处叠加：**每一步都要重新推理一次**（模型调用本身又慢又费），而**每一次推理又都要重新读一遍全量 schema**。步骤越多、工具越多，两者相乘。

值在一处，而且这一处很硬：**「下一步该干什么」永远是看过真实结果之后才决定的**，并且 agent 拿到的是一次边界清晰的单个请求——风险判定、审批、幂等执行、审计留证这套四段式天然就卡在这个节点上，无需额外设计。

## Code Mode

<Badge type="info" text="路径二 · openai/codex" />

``

exec 工具是一个 *freeform grammar* 工具：模型不再发 `tool_use`，而是**直接写一段 JavaScript 源码**，交给 V8 运行时执行。多个工具调用被压进一段紧凑的程序里，省掉的是「一堆完整 schema」外加「每个工具一次模型往返」。

- **自报收益**：总 token 降约 30–50%
- **自报质量**：pass rate 持平或更好
- **独立验证**：无

数字来自上游 PR 说明，属自报，未经第三方复现。

**同一个任务** · 加粗行 = 一次模型往返

| 谁 | 做什么 |
| --- | --- |
| **模型** | **一次性写出整段 JS：查库 → 求和 → 发信<br><small>上下文里没有全量 schema，只有一个紧凑的程序面</small>** |
| agent | 把源码交给 V8 隔离环境执行 |
| V8 | 跑到 `await tools.query(...)`——拿到的是一个真 Promise，**脚本当场挂起**，调用派回宿主 |
| agent | 审批 → 选沙箱 → 试跑 → 被拒后带更宽沙箱重试<br><small>与模型直接发的工具调用同一个入口；要人点头就弹窗，那句 await 一直挂着等人</small> |
| V8 | Promise 兑现，脚本从挂起处往下跑；后两个调用逐个重复上面这两行 |
| agent | 整段脚本的结果按 `TruncationPolicy` 截断后回传 |
| **模型** | **输出最终答复** |

模型往返：**2 次**　·　省下的正是中间那两次重新推理　·　但每次工具调用仍被单独检查过一遍

同一个三步任务。工具调用次数没变、检查次数也没变，变的只是有几次需要惊动模型。图里假定脚本一口气跑完；跑不完会发生什么，见下一节。

### 执行过程中到底发生了什么

有两个问题很容易被并成一个来问，但它们的答案相反：**权限是不是每次都查**（是），**模型是不是每次都被叫回来**（不是）。把这两件事拆开，正是 Code Mode 的全部设计意图——它省的是推理，不是检查。

::: info 问一 · 权限
**整段代码是一口气跑完的吗？中间每次工具调用还查不查权限？**

源码是一口气交出去的，脚本却不是一口气跑完的。每一次工具调用都单独走完整检查，一次也不少。

- `await tools.x(...)` 返回的是一个真 Promise（宿主侧 `v8::PromiseResolver`），V8 在这一行**真的挂起**——不是先把调用攒起来、最后一起结算。
- 调用经 channel 派回宿主，进 `ToolCallRuntime::handle_tool_call_with_source`，**与模型直接发出的工具调用是同一个入口**。
- 随后是 `ToolOrchestrator` 那套固定四步：审批 → 选沙箱 → 试跑 → 被拒后带更宽沙箱重试（不二次审批，靠缓存）。
- 审批优先级：hooks → Guardian 或用户。轮到人时弹窗照弹，脚本那句 `await` 就一直挂着等人按键。
- 沙箱、网络域名策略、`execpolicy` 规则一律照旧生效——脚本跑在 V8 里，但工具**并不在** V8 里执行。
- 全仓 `ToolCallSource::CodeMode` 只出现在遥测、trace 与结果整形里，没有一处出现在审批判定上。
:::

::: info 问二 · 模型
**执行过程中会不会回调模型？**

逐个工具调用不会——这正是 Code Mode 省下来的东西。但控制权确实会在脚本跑完前回到模型手里，而且是默认行为。

- **默认 10 秒就让出一次。**`exec` 的 `yield_time_ms` 默认 `10000`：脚本还没跑完就先把已累积的输出交还，`exec` 返回 `Script running with cell ID ...`，脚本转成后台 cell 继续跑。模型接着用 `wait` 取增量输出，或 `terminate: true` 停掉它。
- **脚本也能自己让出**：`yield_control()`，输出交还、自己继续跑。
- **`notify(...)` 是单向推送**：立刻注入一条 `custom_tool_call_output`，并不交还控制权。
- 让出之后模型与脚本是**并发**的，不是脚本停下等模型批准下一步。「下一步干什么」仍然是写脚本那一刻定的——让出给的是「看一眼」的机会，不是「插手」的机会。
- 唯一会在执行途中被调用的模型是 **Guardian**：一个独立审查会话，在自动审批档代替用户裁决单次动作，超时或输出不合法一律 fail closed。它判的是「这一次动作准不准」，不是「下一步该干什么」。
:::

| 问的是 | 答案 | 源码坐标 |
| --- | --- | --- |
| 每次 `tools.x()` 走不走审批与沙箱 | 走，且与顶层工具调用同一条路 | tools/orchestrator.rs |
| 每次 `tools.x()` 惊不惊动主模型 | 不惊动 | code_mode/delegate.rs |
| 审批需要人点头时 | 弹窗照弹，JS 挂在 `await` 上等 | tools/approvals.rs:503 |
| 脚本跑完前控制权会不会回到模型 | 会——默认跑满 10 s 就让出一次 | DEFAULT_EXEC_YIELD_TIME_MS |
| 途中被调用的模型 | 只有 Guardian 审查会话（自动审批档） | core/src/guardian/ |

坐标相对 `codex-rs/core/src/`，核验日期 2026-08-25，读自 `openai/codex` 本地克隆。

### 实现分解

codex 把它拆成了五个 crate：

| crate | 职责 |
| --- | --- |
| `code-mode` | 主体逻辑 |
| `code-mode-protocol` | 共享的 session / runtime / response / tool-definition 类型。从 V8 实现里拆出来，说明它在往可复用方向走 |
| `code-mode-host` | 独立宿主进程。**已于 PR #31500 转正为默认**，`features.code_mode_host = false` 可退回进程内运行时 |
| `code-mode-runtime` | 运行时实现 |
| `v8-poc` | V8 集成原型 |

#### 核心组件（`codex-rs/core/src/tools/code_mode/`）

- `CodeModeExecuteHandler`——在 V8 隔离环境里执行 JS，接受「原始源文本」输入，允许脚本执行后主动让出控制权。
- `CodeModeWaitHandler`——恢复或轮询已让出的脚本，靠 `cell_id` 定位待恢复的计算单元。
- `CodeModeService`——管理执行单元生命周期，提供 `execute` / `wait` / `terminate`。
- `CodeModeSession` / `CodeModeSessionProvider`——执行单元的会话句柄（`execute` / `wait` / `terminate`）。注意它**不是**一个常驻的 JS 环境：每次 `exec` 都在**全新的 isolate** 里跑，变量绑定不跨轮次存活，跨轮次传状态只能走 `store()` / `load()` 的键值对。
- `CodeModeDispatchBroker` / `CodeModeDispatchWorker`——V8 隔离环境与工具注册表之间的桥，确保嵌套工具调用正确回源到核心会话。
- `ExecContext { session: Arc<Session>, turn: Arc<TurnContext> }`——持有会话与轮次上下文，工具权限与状态就是靠它解析的。
- `interrupt_active_cells`——轮次切换或关闭时打断仍在跑的单元。

#### 嵌套工具调用的链路

```text
JS 里 tools.shell_command(...)
  → call_nested_tool(exec, tool_runtime, invocation, cancellation_token)
    → build_nested_tool_payload()
    → tool_runtime.handle_tool_call_with_source()   ← 与普通工具调用同一个入口
      → result.code_mode_result()
```

::: tip 关键事实
PR #14496「Reuse tool runtime for code mode worker」写明：**在启动 code mode worker 之前先创建 turn-scoped 的 `ToolCallRuntime`，让 worker 复用同一个 runtime 和 router**，嵌套工具调用走的就是它。

也就是说，脚本里每一次工具调用**都会绕回核心那套调度**，不是给 Code Mode 单开的一条更松的后门。「一次性丢进沙箱、中间无人过问」是对它的常见误读。
:::

#### 额外的护栏

- **禁止自调用**：`is_exec_tool_name` 命中时直接返回错误——脚本不能再启动一个 Code Mode。
- **输出截断**：`TruncationPolicy` + `truncate_function_output_items_with_policy`。配套的 PR #28467 专门做了「截断了要说清楚」的告警。
- **图像细节过滤**：`can_request_original_image_detail` 按会话权限过滤。
- **错误传播**：PR #15075「Propagate tool errors to code mode」。

#### 兜底那一层：OS 沙箱

与 Code Mode 正交、但同时存在的还有 codex 的沙箱与审批体系：`sandbox_mode` 三档（`read-only` / `workspace-write` / `danger-full-access`），`approval_policy` 四档（`on-request` / `never` / `untrusted` / `granular`）。平台机制是操作系统自带的——macOS 用 `sandbox-exec` 的 Seatbelt profile，Linux 用 `bwrap` + seccomp，Windows 有原生实现。网络默认关，开启后走域名策略，`deny` 永远压过 `allow`。

再往上还有 `execpolicy`：规则外置成 Starlark 文件，`decision` 取 `allow` / `prompt` / `forbidden`，**多条命中取最严**，并且规则自带用例、可用 `codex execpolicy check` 自测。

### 准确率的代价在哪

Code Mode 的风险不在「有没有人管」，在「**下一步该干什么」被提前写死了**。要分两种任务看：

- **下一步与上一步的内容无关**（读 A、读 B、拼起来写 C）——顺序不因数据而变，传统模式那几次「停下来给模型看一眼」本来就是浪费。这类任务 Code Mode 不吃亏。
- **下一步必须看过内容才知道**（先搜、再根据搜到什么决定改哪个文件）——如果模型闭着眼把后续步骤全写死，就是在出发前把整趟旅程定死。**这里才是精度真正的失血点。**

Code Mode 给这件事留了出口：脚本可以**让出控制权**（`yield_control()`，或跑满默认 10 秒自动让出），把已有输出交给模型看。但要留意这个出口的形状——**让出的是输出，不是执行权**：脚本在后台继续跑，模型看到的是一段已经在往前走的流程。要真的「看过再决定」，得让脚本自己先停下来（`exit()` 收尾，下一轮凭 `store()` 留下的状态接着写）。于是「**这一步该不该停下来看」的判断权，从系统固定的节奏变成了模型自己拿主意**——这是一项新增的、模型得具备的能力，不是白给的。

::: warning 两个传统模式基本不会遇到的新麻烦
**一、中间结果会被主动截断**。省 token 本就是 Code Mode 的目的，一段脚本里连续多次调用产生的输出不会原样全塞回模型。关键信息若恰好落在被截掉的部分，模型看到的是一份缩水的结果。

**二、报错处理的负担转移到了模型写的代码里**。传统模式下某步失败，错误信息自然回到模型手里重新想办法；Code Mode 下得靠模型*提前*写好容错，没料到的失败可能让后面整段代码一起崩掉，而不是温和地把错误交回来讨论。

另外，「pass rate 持平」这类整体指标，未必捕捉得到「没报错、但因为没看见关键中间信息而悄悄给错答案」——这类失败会被记成「任务成功」。
:::

## Tool Search

<Badge type="info" text="路径三 · Claude Code" />

``

与 Code Mode 是同一道题的另一个答案，但它**不动「工具是 schema」这个前提**，只把工具定义从「全量前置」改成「延迟加载 + 按需检索」。

官方把问题定义得很直白：

- **50 个工具的定义**：占 10–20K token
- **准确率拐点**：超过 30–50 个工具后，选择准确率开始下降
- **目录上限**：10,000 个工具
- **每次搜索返回**：最多 5 个

注意第二条：这不只是省钱，**工具太多本身就会让模型挑错**。Tool Search 同时在治这两件事。

**同一个任务** · 加粗行 = 一次模型往返

| 谁 | 做什么 |
| --- | --- |
| **模型** | **上下文里只有工具摘要，没有 schema。发出 `ToolSearch("订单 销量")`** |
| agent | **在本地已装好的工具目录里检索**，挑出最相关的 5 个，把完整 schema 回传<br><small>不联网、不外查——目录早在会话建立时就在客户端进程里了</small> |
| **模型** | **这才第一次看到这几个工具的说明书，输出 `tool_use: 查数据库`** |
| agent | 与传统模式完全相同的四段式，执行 |
| **模型** | **看结果，输出 `tool_use: 算总和`** |
| agent | 执行 |
| **模型** | **看结果，输出 `tool_use: 发邮件`** |
| agent | 执行 |
| **模型** | **输出最终答复** |

模型往返：**5 次**　·　比传统模式还多一次　·　省的不是往返次数，是每次往返携带的前缀体量

这张图是理解 Tool Search 的关键：它省的维度和 Code Mode 正好相反。

### Claude Code 具体怎么实现

- **默认开启**。工具定义不进上下文，模型拿到的是一份工具摘要。
- **装上就留**。搜到并装载的工具在后续轮次一直可用，不必反复搜。
- **压缩会驱逐**。对话长到触发上下文压缩时，装过的工具可能被移走，模型需要再搜一次。
- **核心内置工具永远前置**（`Bash` / `Read` / `Edit`），**且不计入阈值**。
- **启用阈值可配。**`ENABLE_TOOL_SEARCH=auto` 的判据是「可延迟的工具定义 token 占上下文窗口 10%」时启用；`auto:5` 即 5%。
- **命名会影响命中率**。官方建议叫 `search_slack_messages` 而不是 `query_slack`，描述里要带具体关键词；还可以在系统提示词里加一段说明有哪些工具类别。

#### 与缓存的咬合

这一条容易被略过，但它是 Tool Search 能成立的结构性理由：**延迟加载的工具发生变化时只是「追加」，不动缓存前缀**；而前置加载的工具一变，整条缓存立刻作废。换句话说，动态工具集和缓存前缀稳定这两件事，在这个设计下并不冲突。

#### 代价

- 第一次发现工具要多花**一次往返**。
- **工具少于约 10 个时，全量前置反而更快**——这时候开 Tool Search 是净亏。

::: tip 本次会话里的实证
这不是纸面机制。本次对话开始时，`WebSearch` 与 `WebFetch` 并不在可直接调用的工具列表里——系统只给了一串工具名，标注为 deferred。需要查资料时，实际发生的是一次 `ToolSearch(query: "WebSearch WebFetch")`，随后这两个工具的完整参数 schema 才进入上下文，之后才被调用。

返回速度与返回内容的形态（结构化的参数定义，而非网页文字）都指向同一件事：**检索发生在客户端本地那份工具目录里。**
:::

## 装配期静态裁剪

<Badge type="info" text="本项目 · §9.5" />

``

`docs/architecture/运行时内核.md` §9.5「工具数量爆炸的应对」把选项列成两个，**当前采用的是方案 B**：

|   | 方案 A · 服务端工具检索 | 方案 B · 装配期静态裁剪（在用） |
| --- | --- | --- |
| 做法 | 把非核心工具标成按需加载，让模型自己检索取用 | 按 `AgentDefinition.tools` 的选择器，在装配时就把用不上的工具裁掉 |
| 决定的时刻 | 运行中，模型现场判断 | Run 启动前，配置的人提前定死 |
| 依赖 | **provider 特性**，不能假设跨 provider 可用；未进能力表的 profile 一律按不支持处理（§9.8） | provider 无关，零依赖 |
| 缓存 | 追加而非替换 schema，不破坏缓存前缀 | Run 内工具集固定，前缀天然稳定 |
| 短处 | 要额外做能力协商与降级路径 | 灵活性差；工具规模大了会圈不住 |

§9.5 的原话是：「**先用方案 B，工具数真的撑不住了再上方案 A。**」理由是方案 B 零依赖、行为确定、缓存前缀天然稳定；方案 A 是 provider 特性，要额外投入。

### 为什么 Code Mode 在本仓是「要开 ADR」而 Tool Search 不是

差别落在不变量 5——**能力只能经 ToolProvider 进入**：

- **Tool Search 不动它**。工具还是工具，变的只是可见性。而且它落在 §5.4 装配期已有的裁剪层里——把「裁」换成「延迟 + 检索」是同一层的改动。
- **Code Mode 动它**。模型写的是任意代码，能力不再只经 ToolProvider 进入；§12 又明说「护栏不是沙箱」，所以 codex 那套「靠 OS 沙箱兜底」的答案不能直接照搬。evidence 里记了一个未验证的接法：把 V8 里暴露的 API 面本身当成 ToolProvider 的投影，让风险判定与审批发生在 API 边界而不是代码文本上。

::: tip 一处待核对
§9.3 记着「工具集不许在会话中途增删——否则整个缓存作废」，并把它列为倾向静态裁剪的理由之一。但 Claude Code 的 tool search 声称延迟工具的变化**只追加、不废前缀**。两句话并不直接矛盾（前者说的是前置工具集），但把它们摆在一起会发现：**「动态工具集必然废缓存」这个隐含推论并不成立**，因而它作为选方案 B 的论据是偏弱的。方案 B 的真正强论据是「provider 无关」，不是缓存。
:::

## 三条路放在一起

<Badge type="info" text="对照" />

``

|   | 传统 tool_use | Code Mode | Tool Search |
| --- | --- | --- | --- |
| 模型输出什么 | 一个 `tool_use` 块 | 一整段 JavaScript 源码 | 一个 `tool_use` 块（其中一种是搜工具） |
| schema 在哪 | 全量前置在上下文里 | 压成一个紧凑的程序面 | 不进上下文，只有摘要；按需装载最相关 5 个 |
| 三步任务的模型往返 | 4 次 | **2 次**（更少） | 5 次（更多） |
| 工具调用之间回不回模型 | 每一次都回——那就是它的机制 | 逐个调用不回；脚本跑满默认 10 s 会让出一次输出 | 每一次都回，与传统相同 |
| 每次工具调用查不查权限 | 查 | **查**——同一个入口、同一套四步 | 查 |
| 省的是哪一项 | — | 往返次数（重新推理的成本） | 每次往返的前缀体量 |
| 「下一步干什么」何时定 | 每一步看过结果后现定 | 写脚本时一次性定（让出让的是输出，不是执行权） | 每一步看过结果后现定 |

| 动不动「能力只经 ToolProvider」 | 不动 | **动** | 不动 |
| 自报收益 | — | token 降 30–50%，pass rate 持平或更好 | 省掉 50 个工具的 10–20K token；缓解 30–50 个工具后的选择准确率下降 |
| 主要代价 | 往返多、前缀大，两者相乘 | 结果被截断、报错要模型自己兜、需要 JS runtime 与沙箱 | 首次发现多一次往返；工具少于约 10 个时反而更慢 |
| 对缓存前缀 | 工具集一变即作废 | 未核到 | 延迟工具只追加、不废前缀 |
| 规模上限 | 30–50 个工具后开始退化 | 不受 schema 数量直接约束 | 目录 10,000 个工具 |

::: tip 一句话记住三者的关系
**Code Mode 与 Tool Search 都在治「工具太多」，但省的维度正相反**——前者减少惊动模型的次数，后者减少每次惊动时携带的体量。两条并不互斥，可以叠加；而 Code Mode 是唯一一条要换掉前提、动到不变量的。
:::

## 三个容易搞混的点

<Badge type="info" text="澄清" />

``

### 一、Code Mode 不等于「丢进沙箱就没人管了」

准确的图景是：脚本执行到要动真格的那一行时会暂停，把这一次具体的调用**回源到核心**，走与普通工具调用同一个 `ToolCallRuntime` 入口；结果回填之后脚本才继续往下跑。OS 沙箱依然存在，但它是最后一道兜底墙，不是唯一防线。「审批被绕开」是误读；被挪动的是**触发点的位置**——从「两次模型输出之间的间隙」挪到了「脚本执行到某一行的那个瞬间」。

### 二、Tool Search 搜的是本地目录，不是互联网

工具定义从来就不是散落在网上、需要临时搜才知道有什么的东西。内置工具编译在客户端里；MCP 工具在连接建立时就由对方报了过来；skill 与自定义命令是从本地文件系统扫出来的。**整份工具目录在会话开始时就完整地待在 agent 客户端进程里**。唯一沾网的是「模型跑在远端，所以任何工具调用都要走一次模型与客户端之间的往返」——这是所有工具调用共有的，不是 Tool Search 特有的。

### 三、「搜」这个动作由 agent 执行，不是模型自己翻目录

`ToolSearch` 本身也只是 agent 提供的众多工具里的一个，与 `Bash`、`Read` 没有本质区别——只不过它执行完返回的内容恰好是「另外几个工具的说明书」。模型做的仍然只是提出请求；**检索能力属于 agent，模型没有直接执行检索的能力。**
